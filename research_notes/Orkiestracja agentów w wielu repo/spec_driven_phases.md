# Spec-driven, phase-gated workflows for AI coding agents (refinement -> brainstorming -> spec -> plan -> implementation -> review) and their mapping onto an orchestrator and subagents

Research date: 2026-11-23. Sources from 2025 are marked "(2025, possibly outdated)". Where a claim comes only from
a search-result snippet and the page itself was not read, it is marked "(snippet only)". Tool docs pages carry no
publication date; they were read on 2026-11-23 and describe the then-current version.

## 1. How the main frameworks structure phases, artifacts and gates

### Takeaway
All frameworks share the same skeleton (intent -> behaviour spec -> technical design/plan -> task list -> implement -> verify),
and differ mainly in (a) how many files they produce, (b) whether gates are mandatory or optional, and (c) whether the spec
is a per-change document (Spec Kit, Kiro, superpowers) or a living system spec updated by deltas (OpenSpec, Tessl's aspiration).
In every framework the human approves intent/spec and the plan; no framework has an agent as the final approver of intent, and
several (Spec Kit checklists, BMAD "built" vs "done") explicitly forbid the implementing agent from self-approving.

### Cited Findings

**Vocabulary (Böckeler taxonomy)**
- Three levels: spec-first (spec written first, used for the task at hand), spec-anchored ("The spec is kept even after the task is complete"), spec-as-source ("the human never touches the code"). All SDD approaches she found are spec-first; a spec is distinct from a "memory bank" (rules files, product/codebase descriptions that apply to all sessions). (15 Oct 2025, possibly outdated) — [Böckeler, martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**GitHub Spec Kit**
- Core sequence per the docs home: "Specify → Plan → Tasks → Implement → Converge"; each phase "produces a Markdown artifact that feeds the next" — [Spec Kit docs](https://github.github.com/spec-kit/)
- Commands and artifacts (current command reference): `constitution` (principles "that every later phase is evaluated against", run "once up front"); `specify` (spec.md, the what/why, plus built-in `checklists/requirements.md`; the only command "strictly required before `/speckit.plan`"); `clarify` (asks up to five targeted questions about underspecified areas, answers are "encoded back into `spec.md`", an "optional quality gate"); `checklist` ("unit tests for your requirements"; custom checklists are "reviewer-owned", "implementation must not silently self-approve them"); `plan` (plan.md and design artifacts from human-supplied stack/constraints); `tasks` (dependency-ordered tasks.md: Setup, Foundational, one phase per user story in priority order, Polish; parallel markers); `analyze` ("read-only" cross-artifact consistency check over spec.md, plan.md, tasks.md, "never edits files", e.g. finds a task with no matching requirement, "optional quality gate" before implementation); `implement` (runs tasks in dependency order; counts unchecked checklist items and "asks before proceeding when any are unchecked"); `converge` (append-only assessment of code against spec/plan/tasks, may only append tasks to tasks.md; "✅ Converged — the implementation satisfies the spec, plan, and tasks") — [Spec Kit command reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Per-feature layout and methodology text: `specify` creates a feature branch and `specs/[branch-name]/spec.md` with auto-incremented numbers; `plan` adds plan.md, research.md, data-model.md, contracts/, quickstart.md; `tasks` "Marks independent tasks `[P]` and outlines safe parallel groups". Philosophy: "Specifications don't serve code—code serves specifications." Plan-template gates: Simplicity ("Using ≤3 projects?"), Anti-Abstraction, Integration-First ("Contracts defined?", "Contract tests written?"), test-first file order "contract → integration → e2e → unit" — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Human role per README: "reviewing each result before continuing". Extensions add whole processes: a bug flow (`bug-assess`, `bug-fix`, `bug-test`, reports in `.specify/bugs/<slug>/`, only `verified` counts) and an idea-assessment flow (`assess-intake/research/define/shape/decide`, ending in "go, needs-clarification, or kill", with `decision.md` handed to `specify`). Presets "Adapt templates, commands, terminology, or methodology". Multi-repo is not mentioned. The README news section mentions "Spec Kit 1.0" in an item dated 16 Oct 2026 (release date itself not stated) — [Spec Kit README](https://github.com/github/spec-kit)
- Command spelling differs between pages (`/speckit-specify` in the README, `/speckit.specify` in spec-driven.md and the reference); treat as version/agent-dependent — [README](https://github.com/github/spec-kit), [reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Böckeler's observation: Spec Kit creates a branch per spec, which suggests a spec lives for one change request, i.e. spec-first only despite spec-anchored messaging (2025, possibly outdated) — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**AWS Kiro**
- Three files, three phases: requirements.md (or bugfix.md), design.md ("technical architecture, sequence diagrams, and implementation considerations"), tasks.md ("discrete, trackable tasks"). Spec types: Feature Spec (Requirements-First or Design-First), Bugfix Spec (current / expected / unchanged behaviour), Quick Spec (all three artifacts "in one pass without approval gates"). Available in IDE, CLI, Web, Mobile — [Kiro specs](https://kiro.dev/docs/specs/)
- Requirements use EARS ("Easy Approach to Requirements Syntax"): `WHEN [condition/event] THE SYSTEM SHALL [expected behavior]`. An "Analyze Requirements" step checks for "logical inconsistencies, ambiguities, conflicting constraints, and gaps" before design — [Kiro feature specs](https://kiro.dev/docs/specs/feature-specs/)
- Bugfix regression guard pattern: `WHEN [condition] THEN the system SHALL CONTINUE TO [existing behavior]` — [Kiro best practices](https://kiro.dev/docs/specs/best-practices/)
- Review mechanics: a floating Review button opens "Markdown Review", where the human can "comment on exact passages and send your comments to Kiro at once". Task execution: run one task or all; for all, "Kiro builds a dependency graph of the tasks in your tasks.md and groups independent tasks into waves"; "Waves execute sequentially; tasks within a wave execute concurrently." — [Kiro specs](https://kiro.dev/docs/specs/)
- Changing requirements: edit requirements.md, ask Kiro to update design.md, then "Sync Files" in tasks.md. One spec per feature, not one per codebase — [Kiro best practices](https://kiro.dev/docs/specs/best-practices/)
- Böckeler saw tasks traced to requirement numbers and default steering files product.md, structure.md, tech.md (2025, possibly outdated) — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**BMAD-METHOD**
- Versions: "The stable release is v6.12"; "V7 is in preview alpha on this branch", ETA "mid-November 2026" — [BMAD README](https://github.com/bmad-code-org/BMAD-METHOD)
- Current docs describe a loop of four stages, not a fixed sequence ("The stages describe the kind of help a skill gives, not a sequence to complete"): Clarify (ends with "A clear intent: what should be true, what must not change, what is out of scope"), Plan (requirements in the ticket, shared epic decisions, stories ready to build), Build and verify ("Reviewed, committed code that a person has marked done"), Learn and adjust (retrospective, epic verdict) — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Roles on that page: analyst (brainstorming, deep recon, project context; writes brief/PRFAQ/business case), product manager (PRD or other planning document), product owner (initiative, epics, stories, runs the board, "what's next?"), UX designer, architect, developer (build, build-auto, code-review, walkthrough, e2e test generation, retrospective). No separate scrum-master or QA agent is listed on this page — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Artifacts: a ticket tree of `initiative-*.md`, `epic-*.md`, `tickets.toml` (epics or stories in build order), `deferred-work.md` (split-off work), plus a per-story build plan file; initiative and epic files hold Requirements, Constraints, Done when, Boundaries, References — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Scale-adaptive paths: Trivial, One-session, Epic-sized, Project-sized; "A large hobby project keeps planning light; a small change to a regulated system may not." README: "Small changes go straight to build." — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/), [README](https://github.com/bmad-code-org/BMAD-METHOD)
- Gates: "A build stops at `built`; you, or a script or AI session you direct, mark a story done." For organisations BMAD names five sign-off moments and advises: "Put approvals there rather than inventing new gates."; the fifth (PRFAQ verdict) is conditional (snippet only for the list details) — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/), [Plan inside an organization](https://docs.bmad-method.org/plan/plan-inside-an-organization/)

**OpenSpec**
- Layout: living specs in `openspec/specs`; each in-flight change in `openspec/changes/<name>/` with proposal.md, specs/ (deltas), design.md, tasks.md; archived changes move to `openspec/changes/archive/` with a date prefix and archiving updates the specs. Delta example begins `## ADDED Requirements`, each requirement with WHEN/THEN scenarios — [OpenSpec README](https://github.com/Fission-AI/OpenSpec)
- Commands: default profile `explore`, `propose <change>`, `apply-change`, `archive-change`; expanded profile adds `new-change`, `continue-change`, `ff-change`, `verify-change`, `bulk-archive-change`, `onboard`. The README refers to a 2.0 upgrade path — [OpenSpec README](https://github.com/Fission-AI/OpenSpec)
- Philosophy: "fluid not rigid", "iterative not waterfall", "built for brownfield not just greenfield". Gate: "you review the plan before any code is written"; it recommends clearing context before implementation. Its own comparison: Spec Kit is "Thorough but heavyweight"; Kiro is "Powerful but you're locked into their IDE and limited to Claude models" (vendor's claim about competitors) — [OpenSpec README](https://github.com/Fission-AI/OpenSpec)

**Agent OS (Builder Methods)**
- Self-description: "a lightweight system for defining and managing your coding standards in AI-powered development". Four-step workflow: discover standards, inject standards, product planning, shape spec; "in v3, it discovers and documents those standards for you"; shaping questions are "run in plan mode"; outputs are markdown under `agent-os/`. I.e. v3 leans on the host agent's plan mode instead of its own multi-phase spec pipeline — [Agent OS](https://buildermethods.com/agent-os)

**Tessl**
- Böckeler (2025): the only one of the three explicitly aspiring to spec-anchored and exploring spec-as-source; 1:1 spec-to-code-file mapping, generated files headed "GENERATED FROM SPEC - DO NOT EDIT", regeneration from the same spec gave different results (possibly outdated) — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Registry open beta and Framework closed beta were announced in September 2025 (snippet only) — [Tessl launch post](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry/)
- A 2026 third-party review says the Framework did not appear generally available as of mid-2026 and describes a January 2026 pivot toward skills/"agent enablement" (snippet only, unconfirmed by Tessl) — [codemyspec review](https://codemyspec.com/blog/tessl-review)
- The installable artifact today is a methodology "tile" teaching agents to gather requirements, write specs, get approval, then implement and test (snippet only) — [Tessl registry](https://tessl.io/registry/tessl-labs/spec-driven-development)

**Superpowers (obra/superpowers; local installed copy is 7.0.2)**
- Workflow per README: brainstorming ("Activates before building anything") -> using-git-worktrees ("after design approval") -> writing-plans ("bite-sized tasks (2-5 minutes each)", exact file paths, complete code, verification steps) -> subagent-driven-development ("fresh subagent per task with a review after each (most thorough)") or executing-plans (inline, one whole-branch review, "cheapest") -> test-driven-development (RED-GREEN-REFACTOR) -> requesting-code-review ("Critical issues block progress") -> finishing-a-development-branch (merge / PR / keep / discard). Human gates: design sign-off, "go" on the plan, choice at finish — [superpowers README](https://github.com/obra/superpowers)
- Brainstorming hard gate: "Nothing gets built until your human partner approves the design doc". Design doc contents: intent and why; goals, non-goals, anti-goals; constraints; approaches; decided parts of the how; what is left to the builder. Saved to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Plan saved to `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`; required header: Goal, Architecture, Tech Stack, Spec, Global Constraints, Review Focus — [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

**Claude Code (current best-practices page)**
- The page no longer centres on "plan mode"; the documented spec flow is: "Interview me until you could write the spec, then write it to SPEC.md", then "Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done. It's also the file you'll point the reviewer at later" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- `/batch` "splits the work into 5 to 30 units and shows you the plan. Once you approve it, each unit gets its own worktree and opens a PR" — a built-in plan-approval gate before fan-out — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

**GitHub Copilot in VS Code (Plan agent)**
- The Plan agent "researches your project, asks clarifying questions, and creates a plan for you to review before implementation"; the plan includes "implementation steps, relevant files, and verification steps". In the local harness the plan agent "researches your project without editing project files" and stores the plan in session memory at `/memories/session/plan.md`, "not as a project file" — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)
- Review card actions: Implement Plan, Approve Plan Only, Implement with Autopilot, Reject. "Approving a plan and approving tool actions are separate decisions." Inline comments via Submit Feedback "sends your overall and inline comments to the agent without approving implementation"; "Pending feedback disables approval until you submit or clear it." Handoff to another session "shares the plan rather than transferring the entire conversation." — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)

### Inferences
- The three artifacts every framework ends up with are: a behaviour document the human approves, a technical plan the human approves (or delegates), and a machine-executable task list the human usually does not read line by line. A cross-repo process needs the first to be feature-level and the last to be per repo; the middle one is where the split happens.
- The newer generations (BMAD v7 docs, OpenSpec 2.0, Agent OS v3, Spec Kit extensions/presets, Kiro Quick Spec) all moved toward optional gates and size-adaptive paths. The 2025 "fixed pipeline with N mandatory documents" form is being abandoned by its own authors.
- OpenSpec's change-folder + delta + archive model is the only one that directly gives the human a "diff of the spec", and the only one whose living spec survives the change.

### Gaps
- The classic BMAD v4/v6 structure named in the question (Analyst -> PM -> Architect -> Scrum Master -> Dev -> QA, story files, phases Analysis/Planning/Solutioning/Implementation, implementation-readiness check) was not re-verified in this session; the current docs site uses the Clarify/Plan/Build/Learn vocabulary and a ticket tree, and lists a product owner instead of a scrum master. It is unclear whether the docs site describes v6.12 or the v7 alpha.
- The full list of BMAD's five sign-off moments was not read (page excerpt only).
- Spec Kit `taskstoissues` and the existing-projects (brownfield) guide were not read; Spec Kit 1.0 release date not confirmed.
- Tessl's current product state is known only from snippets and a third-party review.
- Kiro's correctness properties / property-based testing are listed as a capability but not described on the pages read; no Kiro statement on multi-root or cross-repo specs was found beyond "central specs repository" advice (section 4).

## 2. Which phases benefit from subagents and which stay in one conversation with the human

### Takeaway
Sources agree on a split: dialogue with the human (refinement, brainstorming, approval) stays in the main conversation; read-heavy
exploration and independent review are the two clear wins for subagents; implementation is delegated one task at a time and
sequentially, not in parallel, unless tasks are provably independent. Delegation is justified by parallelism, noise isolation
and reviewer independence, not by "better answers" or context saving.

### Cited Findings
- Subagents pay off for: "Running independent pieces of work at the same time", "Keeping long output, like a full test run or a wide search, out of your main conversation", "Getting a reviewer that hasn't seen how the code was written", and "Giving a task fewer tools than the main session has, like a reviewer that can read but not edit" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Costs: "a fresh subagent first has to gather context your conversation already had, so it can end up *slower* than doing the task where you are." Outdated advice list: "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help, because it hasn't seen your reasoning, which is a different thing from delegating." and "Running out of context is rarely the problem anymore." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Multi-agent systems "excel at valuable tasks that involve heavy parallelization"; domains needing shared context or many inter-agent dependencies are "not a good fit for multi-agent systems today"; "most coding tasks involve fewer truly parallelizable tasks than research"; agents use "about 4× more tokens than chat interactions" and multi-agent systems "about 15× more tokens than chats"; each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; subagents writing results to external storage and returning references avoids the "game of telephone" (13 Jun 2025, possibly outdated) — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Brainstorming stays with the human: one question at a time, only when the answer changes what gets built; "Look before you ask" (read the project first, never ask what the context already answers); process decisions are the agent's calls and are announced. The only subagent in the phase is a single "builder check": a fresh subagent reads the design doc and lists what a builder could not act on — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Planning research is read-only and can use subagents: Copilot's Plan agent researches "without editing project files"; subagents "handle focused research that returns to the current conversation" — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)
- Implementation: "Fresh subagent per task + task review (spec + quality) + broad final review"; "Never dispatch multiple implementation subagents in parallel (conflicts)."; implementers "must never spawn subagents"; review comes only from the controller; subagents never inherit session history and "Never make a subagent read the whole plan file." Use it when tasks are mostly independent; tightly coupled tasks call for inline execution — [subagent-driven-development SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Counter-example allowing parallel implementation when a dependency graph proves independence: Kiro "groups independent tasks into waves"; "tasks within a wave execute concurrently"; Spec Kit marks `[P]` tasks — [Kiro specs](https://kiro.dev/docs/specs/), [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Fresh context between spec and build: Claude Code ("start a fresh session to build from it"), OpenSpec (clear context before implementation), BMAD (a build session "started in a fresh chat", roughly 500 changed lines excluding tests and one goal) — [Claude Code](https://code.claude.com/docs/en/best-practices), [OpenSpec](https://github.com/Fission-AI/OpenSpec), [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Anthropic's long-running harness uses a role split by session rather than by concurrent agents (initializer session, then incremental coding sessions) and states "it's still unclear whether a single, general-purpose coding agent performs best across contexts" versus specialised testing/QA agents (26 Nov 2025, possibly outdated) — [Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Phase-to-role mapping (compiled)**

| Phase | Where it runs | Why (source) |
|---|---|---|
| Refinement / brainstorming | Main session with the human | Dialogue, one question at a time (superpowers brainstorming) |
| Codebase exploration | Parallel read-only subagents, results returned as files/summaries | Wide search output kept out of main context; parallelism (Claude Code; Anthropic 2025) |
| Spec writing | Main session (it holds the dialogue) | Spec is the product of the dialogue (Claude Code SPEC.md flow) |
| Spec / plan review | One fresh subagent, read-only | Independence from the author's reasoning (Claude Code; superpowers builder check; Spec Kit analyze is read-only) |
| Plan writing | Main session or a planning subagent per repo | Read-only research then a reviewable plan (Copilot Plan agent) |
| Implementation | Fresh implementer per task, sequential within a repo | Conflicts when parallel (superpowers); parallel only across independent waves (Kiro) |
| Task review, final review | Fresh reviewer subagents; strongest model for the final | superpowers model selection |
| Approval | Human, in the main session | All frameworks |

### Inferences
- In a session tree, the root session should own the human dialogue, the feature-level spec, and the status ledger; child sessions should be either read-only (explorers, reviewers) or write-scoped to exactly one repo/worktree (implementers). This follows directly from "shared context and many dependencies are a bad fit" plus "never parallel implementers on the same tree".
- Cross-repo work is the one place where parallel implementation is structurally safe: separate repos mean separate working trees, so one orchestrating child per repo can run concurrently, provided the cross-repo contract was fixed in the feature spec first. No source states this explicitly; it is an extrapolation from Kiro waves and the superpowers conflict rule.
- Depth beyond two levels is not endorsed by the sources read: superpowers forbids implementers from spawning subagents. A three-level tree (feature orchestrator -> repo orchestrator -> task implementer/reviewer) is therefore an extension that needs its own rule about who reviews what.

### Gaps
- No source measured subagent vs single-session quality for the dialogue phases; the split there is prescriptive, not empirical.
- Anthropic's 2025 multi-agent post predates 1M-token contexts; its token multiples (4x, 15x) may no longer hold.
- No source found on nested (depth > 2) agent trees for coding with evidence of outcomes.

## 3. What a good refinement phase produces, and how open questions reach the human

### Takeaway
The converging output is a short intent record: problem and why, goals, non-goals, constraints, acceptance criteria in a testable
form (EARS or WHEN/THEN), and an explicit open-questions list. The shared rule for unknowns is "mark, do not guess": tag the
ambiguity inline, batch the questions that only the human can answer, cap their number, and write the answers back into the spec.

### Cited Findings
- Spec Kit template rules: "Mark all ambiguities: Use [NEEDS CLARIFICATION: specific question]"; "Don't guess: If the prompt doesn't specify something, mark it"; checklist item "No [NEEDS CLARIFICATION] markers remain." — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Spec Kit `clarify` asks up to five targeted questions per run, can be focused on an area and repeated; answers are "encoded back into `spec.md`" — [Spec Kit command reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Spec Kit's assess extension ends refinement with an explicit decision "go, needs-clarification, or kill" and resolves unknowns by "editing the existing Markdown artifacts" rather than rerunning stages — [Spec Kit README](https://github.com/github/spec-kit)
- BMAD Clarify ends with "A clear intent: what should be true, what must not change, what is out of scope."; reading `[ASSUMPTION]` tags and `Assumption:` / `Open question:` lines is stated to be the human's job; initiative/epic files hold Requirements, Constraints, Done when, Boundaries, References — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Superpowers brainstorming: cover goals, non-goals, anti-goals, prior art, current state without reading it out as a questionnaire; ask only when "the answer would change what gets built", otherwise state a proposed default with the reason. After the builder check, questions are sorted into three piles: answered already (put the answer in the doc), minor (settle it and mark it as the agent's call), and the human's (asked most important first, in one message); then hand over the document with a list of the calls made — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Kiro: requirements as EARS statements; bugfix specs capture current, expected and unchanged behaviour; existing requirements can be imported from Jira/Confluence over MCP or by copying a document into the repo and referencing it — [Kiro feature specs](https://kiro.dev/docs/specs/feature-specs/), [Kiro best practices](https://kiro.dev/docs/specs/best-practices/)
- Context anchoring feature document (under fifty lines): Decisions (each with reason and rejected alternative), Constraints, Open questions (as a checklist), State — [Garg, martinfowler.com, 17 Mar 2026](https://www.martinfowler.com/articles/reduce-friction-ai/context-anchoring.html)
- Enterprise variant: the product owner works with AI on the "what" and "why" in the backlog tool; "Intent requires human review." — [InfoQ, 19 Feb 2026](https://www.infoq.com/articles/enterprise-spec-driven-development)
- Thoughtworks brownfield lesson: rework often comes from unclear intent, hidden assumptions and late-discovered constraints; a spec -> plan -> tasks -> coding -> review lifecycle helped surface these earlier (Radar, Apr 2026, ring Assess) — [Thoughtworks Radar, Spec Kit](https://www.thoughtworks.com/en-au/radar/languages-and-frameworks/github-spec-kit)
- Copilot Plan agent: the user answers questions during research; if unsure, they can ask the agent to recommend an approach and explain trade-offs; open questions are resolved before choosing an implementation action — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)

### Inferences
- A refinement output for a business feature that spans repos, assembled from the above: (1) problem statement and why now; (2) goals / non-goals / anti-goals; (3) acceptance criteria with IDs in EARS or WHEN/THEN, including "SHALL CONTINUE TO" lines for behaviour that must not change; (4) constraints; (5) affected systems (repos, services, contracts) as an explicit list; (6) open questions as a checklist, each tagged with who must answer; (7) assumptions the agent made, each marked as the agent's call.
- "Affected systems" is not a standard field in any single-repo framework read; it appears only in the enterprise/multi-repo writing (InfoQ's architect phase). For cross-repo features it has to be added, and it is the input that decides which per-repo children are spawned.
- Routing rule that follows from superpowers and Spec Kit: a child session never asks the human directly and never guesses; it returns a NEEDS_CONTEXT-style status or `[NEEDS CLARIFICATION]` markers to its parent, and only the root session batches questions to the human (capped, most important first). The three-pile sort is the cheapest documented filter.

### Gaps
- No source defines a refinement template specifically for cross-repo business features; the field list above is a synthesis.
- No evidence was found on the right cap for questions (Spec Kit's five per run is a design choice, not a measured optimum).

## 4. Splitting a feature spec into feature-level and per-repo specs; decomposition and traceability

### Takeaway
The documented multi-repo pattern is a layer above the service repos (a dedicated spec repo, a coordinator repo, or the backlog
tool) holding the feature-level spec and system invariants, with per-repo technical plans and task lists living in each repo
next to the code. Decomposition is feature/initiative -> per-repo sub-issue (or epic -> story) -> task, and traceability is kept
with requirement IDs (FR-001 style) carried into tasks, tests and PRs. Mainstream tools still assume one repo.

### Cited Findings
- "enterprise systems are rarely mono-repos"; the article asks where the spec lives when a feature needs changes across "six different repositories"; architecture decisions, business acceptance criteria and task lists change at different rates and have different reviewers, yet tools group them in one feature folder — [InfoQ, 19 Feb 2026](https://www.infoq.com/articles/enterprise-spec-driven-development)
- Proposed flow: Discover (product owner, what/why, in the backlog) -> Design (architect): "For features spanning multiple repositories, this phase breaks down the parent story into repository-specific sub-issues." "Crucially, these sub-issues remain in the backlog." -> Task (developer): implementation tasks are detailed in each repository because they are "tightly coupled with the codebase they'll modify". "business context stays visible on product boards while technical implementation details remain in the repositories themselves"; "progress updates flow back to backlog tools"; an OpenSpec example maps propose / apply / archive to Todo / In Progress / Done. Architects document repository boundaries, integration patterns and constraints so an agent can generate the per-repo sub-issues — [InfoQ, 19 Feb 2026](https://www.infoq.com/articles/enterprise-spec-driven-development)
- Normal Computing: a dedicated spec repo is "the single source of truth for all specifications" with `specs/` (feature specs), `full-spec/` (complete system documentation), templates, memory, `.claude/commands` and `.claude/skills`; a constitution holds system-level invariants (service architecture, stack standards, security, quality gates); requirements carry IDs ("FR-001: System MUST highlight all instances of search query"); `/merge <feature>` folds a feature spec into the authoritative full spec; MCP links to Linear (issues, statuses, spec links) and GitHub (PRs, branches). Why Spec Kit did not fit: "Spec Kit expects one workspace, but our system contains several repos."; schemas tied to production data cannot be regenerated; specs were product-heavy and lacked architectural invariants and integration constraints. Specs should be "a first-class artifact that spans all services, not just a single repo." (page date printed as 12.10.2025; possibly outdated) — [Normal Computing](https://normalcomputing.com/blog/building-sdd-for-real-production-systems-sdd-part2)
- Kiro: keep specs in the project repo next to the code; across teams, create a central specs repository and link it with Git submodules, package references or symbolic links; set up review for shared specs that affect multiple projects; one spec per feature — [Kiro best practices](https://kiro.dev/docs/specs/best-practices/)
- SpecD (open source) lets one project declare several spec workspaces, each pointing at a different directory or repo, so a coordinator repo governs specs across a microservice architecture (snippet only) — [specd](https://github.com/specd-sdd/specd)
- A Microsoft guide recommends linking requirements, specs, tasks, tests and pull requests with shared IDs (snippet only) — [Microsoft Tech Community](https://techcommunity.microsoft.com/blog/educatordeveloperblog/spec-driven-development-for-ai-enabled-enterprise-systems/4520807)
- BMAD decomposition: initiative -> epic -> story, with `tickets.toml` listing epics or stories in build order and a per-story build plan; larger paths "add context and repeat smaller units" — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Superpowers scope rules: if the work is several independent projects, agree on an order and brainstorm them one at a time; if a spec covers multiple independent subsystems, write separate plans, one per subsystem, each producing working, testable software on its own. Tasks declare Interfaces (Consumes / Produces with exact signatures) — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Traceability checks inside one repo: Kiro tasks traced to requirement numbers (Böckeler, 2025); Spec Kit `analyze` reports a task with no matching requirement; superpowers plan self-review "Spec coverage: every requirement maps to a task"; Spec Kit tasks.md is grouped by user story — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [Spec Kit reference](https://github.github.com/spec-kit/reference/agentic-sdd.html), [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Contracts first: Spec Kit's Integration-First gate asks "Contracts defined?" and "Contract tests written?" before implementation, with a `contracts/` directory in the plan output — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)

### Inferences
- Layering that fits the sources: (L0) system invariants / constitution and ADRs, long-lived, in a coordinator location; (L1) feature spec: behaviour, acceptance criteria with IDs, cross-service flows, and the contracts between components (API shapes, events, shared types), in the coordinator location; (L2) per-repo plan: which L1 requirement IDs and which side of which contract this repo implements, plus the task list, stored in that repo; (L3) tasks, each citing the requirement IDs it satisfies.
- The contract is the hinge of the split: once the L1 contract is approved, per-repo work is independent (superpowers "Consumes / Produces", Spec Kit "contracts/"), which is what makes per-repo child sessions safe to run concurrently. A contract change discovered mid-implementation must go back to L1 and to the human, not be patched locally in one repo.
- A coverage matrix (requirement ID x repo x task x test/PR) is the cross-repo equivalent of Spec Kit `analyze`; no tool read produces it across repos, so the orchestrator has to.
- The InfoQ lifecycle argument (acceptance criteria, architecture decisions and task lists age differently) supports keeping L1 durable and treating L2/L3 as disposable after merge.

### Gaps
- No primary source read describes an agent-run, end-to-end cross-repo decomposition with outcome data; InfoQ is a proposal with no metrics, Normal Computing does not describe the per-repo mapping, and the Provectus "orchestration repo above service repos" account was seen only in secondhand social posts and is not cited.
- No documented convention was found for versioning a cross-repo contract during a feature (e.g. provider-first merge order, consumer-driven contract tests driven by agents). The multi-repo tooling researcher may cover this.
- SpecD and the Microsoft guide were not read in full.

## 5. Task granularity for delegated implementers, review loops, and evidence

### Takeaway
Working practice is a task small enough to carry one test cycle and one review (superpowers), or one goal of about 500 changed
lines (BMAD), with exact files, interfaces, test-first steps and a verification command, handed to a fresh implementer with only
that task's brief. The documented loop is: task review covering spec compliance and code quality, capped fix rounds, then one
whole-branch review with a single fix wave. Evidence that these loops improve outcomes is practitioner-level and mechanistic
(reviewer independence); no controlled study of SDD-tool review loops was found, and the one large empirical study on
specification artifacts reports a null result with an important scope limitation.

### Cited Findings

**Granularity and task content**
- README: "bite-sized tasks (2-5 minutes each)" with exact file paths, complete code and verification steps — [superpowers README](https://github.com/obra/superpowers)
- Current writing-plans skill: a step is "one action with a checkable result"; a task is "the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate" and ends with an independently testable deliverable. Task structure: Files (Create / Modify / Test with exact paths), Interfaces (Consumes / Produces with exact signatures), Steps (write the failing test, run it to verify it fails, implement, run to verify it passes, commit). No placeholders: "TBD", "handle edge cases", "add appropriate validation" are failures. Self-review includes spec coverage, type consistency across tasks, and proportion (the plan is not several times longer than the spec) — [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- BMAD: a build session is one goal and roughly 500 changed lines excluding tests; a request with two independent goals is offered a split — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- Spec Kit tasks.md: Setup, Foundational, one phase per user story in priority order, Polish; for large features, staged implement runs and "verify each stage works before moving to the next" — [Spec Kit reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Anthropic harness: without decomposition "the agent tended to try to do too much at once—essentially to attempt to one-shot the app"; fix was a feature list where agents may only change a `passes` field, one feature per session, and end-to-end testing "as a human user would" because Claude tended "to mark a feature as complete without proper testing" (26 Nov 2025, possibly outdated) — [Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Dispatch contract**
- The controller extracts each task to its own brief file; the dispatch carries the task's place in the project, the brief path, interfaces from earlier tasks, ambiguity resolutions and a report-file path. The implementer writes the full report to a file and returns only status, commits, a one-line test summary and concerns. Pasting accumulated history is an anti-pattern (a cited dispatch of 42k characters was 99% pasted history) — [subagent-driven-development SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Implementer statuses and handling: DONE -> review; DONE_WITH_CONCERNS -> read concerns, resolve correctness/scope concerns before review; NEEDS_CONTEXT -> provide context and re-dispatch; BLOCKED -> more context, a more capable model, a smaller task, or a ledgered ruling that the plan is wrong. "Never ignore an escalation or force the same model to retry without changes." (read from the installed 7.0.2 copy of the file at this upstream path) — [handling-reports.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/handling-reports.md)
- Model selection: "Use the least powerful model that can handle each role"; mechanical 1-2 file tasks on a cheap model, integration/judgment on a standard model, architecture and the final whole-branch review on the most capable; mid-tier is the floor for reviewers because cheap models "routinely take 2-3× the turns"; "Always specify the model explicitly when dispatching a subagent." — [subagent-driven-development SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)

**Review loops**
- Per task: "spec compliance AND task quality are both required"; implementer self-review never replaces it; the review package is the diff from the recorded BASE to HEAD (not `HEAD~1`, which "silently drops all but the last commit of a multi-commit task"). Fix loop triggers: spec failure, any Critical or Important finding; rounds 1-3 resume the same implementer, rounds 4-5 escalate a model tier, each round ends with a scoped re-review; past the cap "the failure is structural". Findings may not be silently dropped; every ruling is a ledger entry — [subagent-driven-development SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Per branch: one whole-branch review on the most capable model over a review package from the merge base; if it returns findings, "dispatch ONE fix subagent with the complete findings list — not one fixer per finding" ("a real session's final-review fix wave cost more than all its tasks combined"); exactly one scoped re-review; "There is no second fix wave" — residual load-bearing findings go to the human at the finish step (installed 7.0.2 copy) — [final-review.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)
- Spec Kit post-implementation loop: `converge` compares code with spec/plan/tasks, appends missing tasks, and is repeated with `implement` until "Converged" — [Spec Kit reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Claude Code: `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code."; spec-compliance prompt example: "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style"; a reviewer subagent restricted to `tools: Read, Grep, Glob` cannot edit, and that limit is enforced by the harness — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Over-review warning: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)

**Evidence**
- ESEM 2026 (published 2026-10-05, single author Brenn Hill): 88,052 pull requests in 119 open-source repositories, 25,209 specification artifacts scored; none of five hypotheses derived from SDD vendor claims is supported; after propensity-score matching, specified vs unspecified PRs show no meaningful difference in defect introduction (reported in the search summary as -0.6 percentage points, p = 0.133); specification quality predicts neither defects nor rework; the raw association is attributed to task complexity. Scope limit stated by the paper: the artifacts are "overwhelmingly references to tracking issues and tickets" rather than SDD tool output, "which no repository in the sample commits"; "SDD tool adoption itself remains untested." — [Hill, ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84)
- Counter-evidence at practitioner level: agents do not always follow the spec; in one case an agent marked a verification task as done without writing the unit test (12 Nov 2025, possibly outdated) — [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)
- Thoughtworks Radar (Apr 2026, Assess): teams using Spec Kit mostly in brownfield reported that the lifecycle surfaced unclear intent and hidden constraints earlier, and that experienced engineers with strong clean-code and architecture practice get the most value — [Thoughtworks Radar](https://www.thoughtworks.com/en-au/radar/languages-and-frameworks/github-spec-kit)

### Inferences
- The stable task recipe across sources: one deliverable, explicit files, explicit consumed/produced interfaces, the requirement IDs it covers, a failing test first, the exact command that proves it, a commit. Size heuristics range from "one test cycle + one review" to "about 500 changed lines"; the old "2-5 minutes" wording survives in the superpowers README but the skill text has moved to the deliverable-based definition.
- Review loops need caps and a severity filter to be worth their cost: capped fix rounds, one final fix wave, "skip style", and parking of minor findings are all responses to the same failure (endless reviewer-driven churn).
- Reviewer independence (fresh context, read-only tools, the spec as the reference) is the mechanism every source relies on; it is asserted, not measured, in the material read.
- For a cross-repo feature there is one more review level the single-repo sources lack: a feature-level integration review that checks the per-repo branches against the L1 contract and the acceptance criteria together. Spec Kit `converge` (code vs spec) is the nearest single-repo analogue.

### Gaps
- No controlled or large-sample study was found that measures the effect of per-task or two-stage agent review loops on defects. The ESEM 2026 result does not test SDD tools or review loops.
- An ESEM 2026 paper on AI-to-AI code review (whether reviewers miss defects introduced by the same model) surfaced in search but its PDF could not be read; it may bear on choosing a different model for reviewers.
- No data on the optimal task size for delegated implementers; all figures are authors' heuristics.

## 6. Criticisms, failure reports, and lightweight variants

### Takeaway
The recurring criticisms are: too much markdown to review (review burden moves from code to documents, or doubles), poor fit
for small changes, weak brownfield awareness, agents that still ignore or over-apply the spec, big-batch/waterfall drift, and
spec maintenance cost. The recommended lightweight forms are size-adaptive paths, change-scoped deltas instead of full
specs, a short feature document, small slices, and gates only where a human decision is actually needed.

### Cited Findings
- Problem-size mismatch: Kiro turned a small bug into four user stories with 16 acceptance criteria ("like using a sledgehammer to crack a nut"); for a 3-5 point feature Spec Kit felt like overkill. Review burden: "I'd rather review code than all these markdown files." Agents ignoring/over-applying: research found existing classes but the agent treated them as new and generated duplicates; elsewhere it followed a constitution article too eagerly. Brownfield: for two of three tools, introduction into an existing codebase was harder. MDD parallel: spec-as-source could combine "inflexibility and non-determinism". The term "spec" is also used as a synonym for "detailed prompt" (15 Oct 2025, possibly outdated) — [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Marmelab's list: Context Blindness (agents "often miss existing functions that need updates"), Markdown Madness ("SDD produces too much text, especially in the design phase"), Systematic Bureaucracy, Faux Agile, Double Code Review ("review time doubles"), False Sense of Security ("agents don't always follow the spec"), Diminishing Returns ("For large existing codebases, SDD is mostly unusable."). A Spec Kit spec for a simple date-display feature was "8 files and 1,300 lines of text". Alternative: iterate on the next riskiest assumption with short instructions and "split complex requirements into multiple simple ones" (12 Nov 2025, possibly outdated) — [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)
- Big-batch argument: "The bottleneck was never how fast code gets written. It is the feedback loop."; "Software requirements aren't facts. They are a network of unverified hypotheses."; "Under time pressure, reviews go superficial."; "Human comprehension must scale with delivery, or ownership evaporates." Recommended: the smallest useful slice, continuous integration over gates, production telemetry as ground truth. Concession: SDD may suit stable, well-understood requirements that are easy to verify in bulk. No data cited — [Adamsson, 22 Jun 2026](https://cladam.github.io/2026/06/22/spec-driven-development/)
- Thoughtworks Radar (Apr 2026): Spec Kit in Assess; continually adding context led to instruction bloat and context rot (one team moved reusable guidance into skills); teams reported unnecessary defensive checks and verbose markdown that increased cognitive load; trimming templates (fewer generated files, less console verbosity) helped. A separate "Agent instruction bloat" blip is rated Caution — [Thoughtworks Radar](https://www.thoughtworks.com/en-au/radar/languages-and-frameworks/github-spec-kit)
- Enterprise critique: spec-to-implementation alignment is "the elephant in the room"; for large existing applications "it may be impractical to have an LLM create specs without exceeding context limits", so specs should grow incrementally with each change; tools are developer-centric and not integrated with backlog systems — [InfoQ, 19 Feb 2026](https://www.infoq.com/articles/enterprise-spec-driven-development)
- Empirical null result on specification artifacts in PR workflows (scope limits in section 5) — [Hill, ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84)
- Spec drift: a DZone analysis argues that keeping specs in sync is the same problem teams have long had with docs and READMEs (snippet only) — [DZone](https://dzone.com/articles/spec-driven-development)
- Lightweight variants shipped by the tools themselves: Kiro Quick Spec ("in one pass without approval gates"); BMAD "Small changes go straight to build" and four paths by size and risk; OpenSpec "fluid not rigid", change-scoped proposals with deltas; superpowers: trivial requests done directly, small changes get a short design note, plus labelled throwaway spikes; Spec Kit presets and optional gates; Copilot/Claude Code plan-then-implement inside one session — [Kiro specs](https://kiro.dev/docs/specs/), [BMAD README](https://github.com/bmad-code-org/BMAD-METHOD), [OpenSpec](https://github.com/Fission-AI/OpenSpec), [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [Spec Kit reference](https://github.github.com/spec-kit/reference/agentic-sdd.html), [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)
- Proportion rule as a guard against spec bloat: a plan should not be several times longer than its spec — [writing-plans SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

### Inferences
- The strongest critiques (Böckeler, Marmelab) date from late 2025 and target the first generation of tools; the 2026 tool changes listed above read as direct responses. The critiques that remain unanswered in 2026 are the ones about agents not following the spec and about big batches.
- For a cross-repo business feature the big-batch risk is higher than in a single repo, because the batch is multiplied by the number of repos. The mitigation consistent with the sources is to slice the feature vertically (one thin end-to-end flow across all affected repos first), rather than finishing each repo's full scope in turn.
- A size router at the start of the process (trivial / one-session / multi-repo feature) is the single most commonly adopted remedy and should precede any phase gate.
- Because agents still skip or misreport verification steps, "the spec says so" cannot be the control; an independent check of code against acceptance criteria (converge-style) is the compensating control.

### Gaps
- No quantitative study of SDD tool adoption outcomes (defects, lead time) was found; the ESEM paper explicitly leaves it untested.
- Kent Beck's and Martin Fowler's own critiques were referenced in a search result (a paywalled Level Up article) but not read.
- "Review fatigue" is reported qualitatively only; no measurement of human review time per artifact was found.

## 7. Recording decisions and deferred findings so they survive sessions

### Takeaway
The documented durable carriers are files in git: a decision log or ADRs with explicit status, a short living feature document
(decisions, constraints, open questions, state), a progress/status ledger read at the start of every session, and a
deferred-work file. Conversation memory and automatic compaction are explicitly not trusted. Scratch ledgers are deleted at the
end, so rulings and deferred findings must be copied to a durable place before cleanup.

### Cited Findings
- Feature document as "an ADR in progress": Decisions (with reason and rejected alternative), Constraints, Open questions, State; updated at natural pause points ("a few lines after each significant moment, not a documentation exercise"); shared at the start of each new session; significant decisions graduate to formal ADRs when the feature ships. On compaction: trusting it is "not a strategy; it is a hope." Litmus test: being able to close a session and start fresh without anxiety — [Garg, martinfowler.com, 17 Mar 2026](https://www.martinfowler.com/articles/reduce-friction-ai/context-anchoring.html)
- ADR rules for agents: markdown in `docs/decisions`, rules stated in AGENTS.md; "Treat accepted ADRs as binding." (on conflict the agent stops and proposes changing the task or the ADR); proposed = non-binding context; superseded = historical only. Record durable product/architecture decisions, one rule stated once in the ADR that owns it; do not record debate transcripts, amendment logs (git is the changelog) or small implementation details. Pitfalls: agents "fight tooth and nail to apply an accepted decision even when it is obsolete" (an agent kept an outdated storage abstraction and added a compatibility layer), and "overlitigation" when agents are invited to edit ADRs — [Davidson, O'Reilly Radar, 2 Oct 2026](https://oreilly.com/radar/coding-agents-love-decision-records/)
- Progress file + git as state: the coding agent writes "summaries of its progress in a progress file" and commits; each session starts by reading "the git logs and progress files to get up to speed"; the feature list is JSON whose only editable field is `passes`, because "the model is less likely to inappropriately change or overwrite JSON files" (26 Nov 2025, possibly outdated) — [Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Superpowers ledger: `<workspace>/progress.md`, one line per completed task (`Task <N>: complete (commits <base7>..<head7>, review clean)`), every ruling recorded; "Conversation memory does not survive compaction."; after compaction "trust the ledger and `git log`." — [subagent-driven-development SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- At finish the workspace is deleted, so first every ledger line containing `Ruling:` is collected into the final message under "Rulings I made", each with what it costs if wrong: "A ruling that dies with the workspace was a decision made in secret." The final reviewer is pointed at the ledger's deferred-minor and parked lines to triage what must be fixed before merge (installed 7.0.2 copy) — [final-review.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)
- BMAD keeps split-off work in a `deferred-work.md` file inside the ticket tree — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/)
- OpenSpec keeps history by moving completed changes to `openspec/changes/archive/` with a date prefix while merging deltas into the living specs — [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Spec Kit keeps a decision.md per idea assessment and a constitution under `.specify/memory` — [Spec Kit README](https://github.com/github/spec-kit)
- Standing-instruction file hygiene: CLAUDE.md is loaded into every session, should hold only what cannot be worked out from the code (including "Decisions that aren't in the repo"), and stay short (the memory guide recommends under 200 lines); "If something has to happen every time, make it a hook, a deny rule, or a managed setting." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- Copilot's local Plan agent stores its plan in session memory, "not as a project file", so it does not survive unless saved — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)

### Inferences
- A four-file persistence set covers what the sources describe: (1) ADRs with status for durable cross-feature decisions; (2) a per-feature decision/open-question/state document, kept beside the feature spec; (3) a status ledger per running plan (per repo), machine-appendable, one line per task with commit range and review verdict; (4) a deferred-findings/backlog file committed with the branch. (1), (2) and (4) are durable; (3) is scratch whose rulings must be promoted before deletion.
- For cross-repo features, (2) and the feature-level ledger belong in the coordinator location, while each repo keeps its own task ledger and its own deferred file; the feature ledger should record per-repo branch, commit range and review verdict so a fresh root session can resume from files alone.
- Status fields matter more for agents than for humans: without accepted/proposed/superseded, agents treat stale decisions as binding; with write access, they bloat the record. Human-only promotion to "accepted" is the cheap control.
- Restricting agent edits on status files to one field (Anthropic's `passes`) is a transferable trick for ledgers and coverage matrices.

### Gaps
- No formal study of ADR or memory-file practice with agents was found; sources are practitioner articles. An arXiv preprint on git as agent memory surfaced in search but was not read.
- No source read addresses where a decision log should live when a decision spans several repos.

## 8. Human approval gates and how to make approval cheap

### Takeaway
The recommended gates are few and fixed: approve intent/spec, approve the plan (or the contract-level part of it), and accept
the finished result; everything in between is agent-reviewed. Approval is made cheap by reviewing a delta rather than a whole
document, by inline comments instead of rewrites, by a short list of decisions the agent made on the human's behalf, by batched
and capped questions, and by size-based paths that skip gates for small work.

### Cited Findings
- Gate placement: superpowers — design-doc approval (hard gate), plan review and "go", merge/PR/keep/discard choice at the end — [superpowers README](https://github.com/obra/superpowers); Kiro — per-phase review of requirements, design, tasks, with Quick Spec as the no-gate path — [Kiro specs](https://kiro.dev/docs/specs/); OpenSpec — "you review the plan before any code is written" — [OpenSpec](https://github.com/Fission-AI/OpenSpec); BMAD — human marks a story done, five org sign-off moments, "Put approvals there rather than inventing new gates." — [How BMad works](https://docs.bmad-method.org/start/how-bmad-works/), [Plan inside an organization](https://docs.bmad-method.org/plan/plan-inside-an-organization/); Spec Kit — "reviewing each result before continuing", with reviewer-owned checklists that the implementation "must not silently self-approve" — [Spec Kit README](https://github.com/github/spec-kit), [reference](https://github.github.com/spec-kit/reference/agentic-sdd.html)
- Separation of approvals: "Approving a plan and approving tool actions are separate decisions."; "Approve Plan Only" exists as a distinct action — [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)
- Cheap feedback mechanics: Kiro Markdown Review ("comment on exact passages and send your comments to Kiro at once"); Copilot inline plan comments, with approval disabled while feedback is pending — [Kiro specs](https://kiro.dev/docs/specs/), [VS Code planning docs](https://code.visualstudio.com/docs/copilot/agents/planning)
- Delta review: OpenSpec change folders carry only ADDED (etc.) requirements against the living spec — [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Decision lists: superpowers hands over the design doc "with a list of the calls made", and at the end lists "Rulings I made", each with what it costs if wrong — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [final-review.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)
- Playback instead of documents: describe the understood part back in about 200-300 words and ask what is wrong or missing; first message of about 200 words for a detailed request — [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Question budget: Spec Kit clarify asks at most five questions per run; superpowers asks the human's questions in one message, most important first — [Spec Kit reference](https://github.github.com/spec-kit/reference/agentic-sdd.html), [brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)

### Inferences
- Gate set for a cross-repo feature, derived from the above: G1 intent (problem, goals/non-goals, acceptance criteria, affected systems, open questions answered); G2 feature spec, where the human's attention goes to the cross-repo contract and the list of agent-made assumptions; G3 per-repo plans, approved as a set through a one-page summary (repos touched, requirement coverage matrix, order of merges, risks) rather than plan by plan; G4 result acceptance per repo (PR/merge decision) with the rulings list and deferred findings. Intermediate task reviews stay agent-to-agent.
- The cheapest approval formats found, in order of reading cost: a decision list ("calls I made", each with cost if wrong); a delta against the previous spec; a 200-300 word playback; inline comments on a document. A full-document re-read is the most expensive and the one critics report people stop doing.
- An approval record should be explicit and durable (a status line in the spec or ledger: who approved which version), since plan approval and tool-action approval are separate things and sessions restart.
- Agents pre-screening artifacts (analyze / builder check) reduce what reaches the human but must be read-only and must not be able to mark the gate as passed.

### Gaps
- No source measured how long human approval takes per gate or which summary format gets the most reliable review.
- No source read describes approving several per-repo plans as one set; G3 as a bundled gate is a synthesis.
- BMAD's five sign-off moments (what each judges and blocks) were not read in full.
