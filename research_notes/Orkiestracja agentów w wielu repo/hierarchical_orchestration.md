# Hierarchical orchestrator + subagent architectures for LLM coding agents (nesting to arbitrary depth)

Research date: 2026-11-23. Scope: general agent-architecture evidence only (multi-repo specifics are covered by another researcher).

Reading conventions used in these notes:

- **[OLD]** marks a source older than about 18 months (published before roughly May 2025). **[BORDERLINE]** marks sources from May-June 2025 (about 17 months old).
- "Fetched" means the primary page was read in this session. "Snippet only" means the claim comes from a search-result summary and the page itself was not read (or returned an error), so treat it as unverified.
- Product documentation pages (Claude Code, Codex, VS Code, Copilot, ADK) change often and several show no date; they were read on 2026-11-23.

## 1. What orchestration topologies are documented, and what does each cost in tokens, latency and error rate?

### Takeaway
Five families recur in every vendor's material (pipeline with gates, orchestrator-worker / supervisor, generator-verifier, handoff / swarm, dynamic ledger-based planning), and all of them are sold with the same caveat: start with the simplest thing that works. Measured overhead ranges from about 1.6x to 6x the turns of a single agent in a controlled study, and vendor figures range from "3-10x tokens vs. single agent" to "15x tokens vs. chat"; a hub-and-spoke orchestrator contains error propagation far better than independent parallel agents (4.4x vs. 17.2x error amplification).

### Cited Findings

**Catalogue of topologies**

- Anthropic's base taxonomy: workflows ("LLMs and tools are orchestrated through predefined code paths") versus agents ("LLMs dynamically direct their own processes and tool usage"). Workflow patterns: prompt chaining (with programmatic checks between steps "to ensure that the process is still on track"), routing, parallelization (sectioning / voting), orchestrator-workers ("well-suited for complex tasks where you can't predict the subtasks needed"), evaluator-optimizer ("particularly effective when we have clear evaluation criteria"). Published Dec 19, 2024 **[OLD]**; the page itself now carries a note that the tooling landscape has changed since. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Microsoft's Azure Architecture Center (ms.date 2026-02-12, page updated 2026-09-21) lists sequential, concurrent, group chat (including maker-checker loops), handoff, and magentic (dynamic task-ledger) orchestration, each with "when to use / when to avoid" lists. It characterises magentic as "Slow to converge. Stalls on ambiguous goals." and says its cost is the hardest to predict "because the manager agent continues to iterate until it builds a viable plan". — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- LangChain's current docs list five patterns: Subagents (main agent calls subagents as tools, "All routing passes through the main agent"), Handoffs, Skills (single agent loads prompts on demand), Router, and Custom workflow (LangGraph). — [LangChain docs, Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- OpenAI Agents SDK distinguishes LLM-driven from code-driven orchestration, and within the former "agents as tools" ("A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`") versus handoffs (the "specialist becomes the active agent for the rest of the turn"). Code-driven patterns: structured outputs, chaining, an evaluator loop ("stop when the evaluator says the output passes the required criteria"), and parallel runs. — [OpenAI Agents SDK, Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)
- Google ADK (current docs) describes graph-based workflows, dynamic (code) workflows, collaborative workflows (a coordinator agent that delegates to sub-agents), and template workflows (sequence, loop, parallel). — [ADK, Workflows](https://adk.dev/workflows/)
- Microsoft Magentic-One (Nov 4, 2024 **[OLD]**): an Orchestrator with an outer loop that "manages the task ledger (containing facts, guesses, and plan)" and an inner loop that "manages the progress ledger (containing current progress, task assignment to agents)"; on a stall "it can update the Task Ledger and create a new plan". Four workers: WebSurfer, FileSurfer, Coder, ComputerTerminal. — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- Cursor's long-running coding experiments (Jan 14, 2026) ended on a planner / worker / judge hierarchy after flat designs failed: planners "continuously explore the codebase and create tasks", workers "just grind on their assigned task until it's done, then push their changes", and "At the end of each cycle, a judge agent determined whether to continue, then the next iteration would start fresh." — [Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)
- Anthropic's long-running app harness (Mar 24, 2026) uses planner / generator / evaluator, with agents communicating through files and a "sprint contract" negotiated between generator and evaluator before each sprint. — [Anthropic, Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Cognition (Apr 22, 2026) reports three patterns that work in production for coding: a generator-verifier review loop, a "smart friend" (cheap primary model calls a stronger model as a tool), and manager-with-children delegation shaped as "map-reduce-and-manage". It calls unstructured swarms "mostly a distraction". — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Claude Code documents two shapes: subagents (results return to the caller, "Main agent manages all work") and experimental agent teams (shared task list plus direct teammate messaging, "Self-coordination through messages"). — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)

**Measured cost, latency and error numbers**

- Controlled study of 180 configurations (5 architectures, 3 model families, 4 benchmarks), arXiv 2512.08296 (Dec 2025). Overhead and turns versus a single agent, with all systems matched at about 4,800 reasoning tokens per trial: Independent 58% overhead / 11.4 turns; Decentralized 263% / 26.1 turns; Centralized 285% / 27.7 turns; Hybrid 515% / 44.3 turns; single agent 7.2 turns. Success per 1K tokens: single agent 67.7, Independent 42.4, Decentralized 23.9, Centralized 21.5, Hybrid 13.6. — [Kim et al., Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v2)
- Same study, error amplification factor (multi-agent error rate over single-agent error rate): Centralized 4.4x, Hybrid 5.1x, Decentralized 7.8x, Independent 17.2x. — [Kim et al.](https://arxiv.org/html/2512.08296v2)
- Same study, task dependence: on a parallelizable financial-reasoning benchmark the centralized architecture gained +80.8% over a single agent; on a sequential planning benchmark (PlanCraft) every multi-agent variant lost 39% to 70% (Centralized -50.3%, Independent -70.1%). Mean multi-agent change across everything: -3.5% (95% CI -18.6% to +25.7%). — [Kim et al.](https://arxiv.org/html/2512.08296v2)
- Same study, scaling laws: turns grow super-linearly with agent count (T = 2.72 x (n + 0.5)^1.724); coordination gives diminishing or negative returns once the single-agent baseline exceeds about 45%; tool-heavy tasks are penalised more by multi-agent overhead; per-agent reasoning capacity becomes "prohibitively thin" beyond about 3-4 agents under a fixed budget. A fitted model picked the best architecture for 87% of held-out configurations. — [Kim et al.](https://arxiv.org/html/2512.08296v2)
- Anthropic's research system (Jun 13, 2025 **[BORDERLINE]**): "agents typically use about 4x more tokens than chat interactions" and "multi-agent systems use about 15x more tokens than chats"; "token usage by itself explains 80% of the variance" in performance on their eval. Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval". — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Anthropic's Jan 23, 2026 guidance gives a different baseline: "multi-agent implementations typically use 3-10x more tokens than single-agent approaches", and multi-agent systems "often take longer overall than single-agent systems because of the sheer increase in total computation". — [Claude blog, Building multi-agent systems: when and how to use them](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Claude Code docs: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode". — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- LangChain's worked comparison: Subagents need 4 model calls for a one-shot request (one more than Handoffs/Skills/Router "because results flow back through the main agent"), 8 calls over a repeated request (subagents are "stateless by design"; stateful patterns save "40-50% of calls on repeat requests"), and 5 calls / about 9K tokens on a multi-domain task versus about 15K tokens for Skills and 7+ calls / 14K+ tokens for Handoffs. — [LangChain docs, Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- LangChain benchmark (Jun 10, 2025 **[BORDERLINE]**, gpt-4o, modified tau-bench with distractor domains): a single agent "falls off sharply" with two or more distractor domains while supervisor and swarm stay flat in tokens; supervisor consistently uses more tokens than swarm and scores slightly lower. — [LangChain, Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Anthropic's planner/generator/evaluator harness: a solo run of a retro game maker took 20 min and $9; the full harness took 6 hr and $200 ("over 20x more expensive"). A later run on Opus 4.6 took 3 hr 50 min and $124.70, of which the planner was $0.46, three build rounds $71.08 + $36.89 + $5.88, and three QA rounds $3.24 + $3.09 + $4.06. — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Anthropic's parallel C-compiler project (Feb 5, 2026): 16 agents, nearly 2,000 Claude Code sessions over two weeks, 2 billion input and 140 million output tokens, just under $20,000, about 100,000 lines of Rust. No orchestrator was used ("I don't use an orchestration agent"); agents claimed tasks via lock files. — [Anthropic, Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
- GitHub Copilot CLI production A/B test (Jun 12, 2026) of a more selective delegation policy: 23% fewer tool failures per session, 27% fewer search tool failures, 18% fewer edit tool failures, P95 user wait time 5% lower and P75 3% lower, no quality regression. The authors attribute the gain to reduced orchestration overhead, not faster LLM calls. — [GitHub Blog, How we made GitHub Copilot CLI more selective about delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- MS-Eval (arXiv 2610.22869, Oct 16, 2026; abstract only): across four delegation variants and eight frontier models, main-agent-delegation/sub-agent-execution "generally raises cost, with benefits that depend on the case"; closed-source frontier models saw higher cost and worse performance, open-source models benefited; sub-agent specialization was the best practical variant; "Unnecessary or redundant delegation" is pure overhead. — [Ding et al., MS-Eval](https://arxiv.org/abs/2610.22869)

### Inferences
- The token multipliers are not comparable to each other: 15x is versus a chat turn, 3-10x is versus a single agent on the same task, 7x is agent teams in plan mode versus one session, and 58-515% is coordination overhead at a matched reasoning budget. A report should quote each with its baseline rather than a single "multi-agent costs Nx" figure.
- A feature pipeline (refinement -> brainstorming -> spec -> plan -> implementation) is, in the vendors' vocabulary, a prompt chain / sequential orchestration with gates whose individual stages may fan out (orchestrator-worker) or loop (generator-verifier). The sequential backbone is exactly the task shape where Kim et al. measured multi-agent losses of 39-70%, so the hierarchy should add agents only inside stages that are parallel or verifiable, not between stages that share context.
- The centralized (hub-and-spoke) topology is the one with the best measured error containment, which supports a tree where every child reports to exactly one parent rather than children messaging each other.

### Gaps
- No source gives error-rate or cost numbers per topology for coding tasks specifically; Kim et al. used browsing, finance, planning and workplace benchmarks, and Anthropic's 90.2% figure is a research eval.
- Latency per topology is reported only anecdotally (Copilot CLI percentiles, Anthropic harness wall-clock times); no head-to-head latency benchmark was found.
- The Google ADK documentation was restructured (the old multi-agent page redirects to a workflows overview), so the long-standing ADK pattern list (coordinator/dispatcher, hierarchical task decomposition, generator-critic, etc.) could not be re-verified against a current page.

## 2. What is the evidence for and against deep nesting (depth > 2)? Where does information get lost, and what mitigations are documented?

### Takeaway
No empirical study was found that measures task fidelity as a function of nesting depth for coding agents; the evidence is indirect (per-handoff degradation, product depth caps, practitioner reports). Every shipping coding product caps or discourages depth: Claude Code defaults to three layers below the main conversation, Cursor to two, VS Code local agents to none by default (max five), Devin to one manager level, and several forbid nesting for their team/task modes. The documented mitigations are: write results to files and return references, skip the paraphrasing hop, keep writes single-threaded, and decompose by context rather than by role.

### Cited Findings

**Where information is lost**

- Anthropic names the mechanism: splitting work by role (planner, implementer, tester, reviewer) "creates constant coordination overhead" and causes "the telephone game", with "each handoff degrading fidelity"; in one experiment "the subagents spent more tokens on coordination than on actual work". — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- LangChain measured the upward direction: in the supervisor architecture sub-agents cannot answer the user, so the supervisor relays their output, which the authors compare to a game of "telephone" and blame for most of the supervisor's errors. Removing handoff messages from sub-agent state and adding a `forward_message` tool that passes a sub-agent's response through without paraphrasing gave "a nearly 50% increase in performance on this benchmark". (Jun 10, 2025 **[BORDERLINE]**; baseline values are only in charts.) — [LangChain, Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Cognition's original argument (Jun 12, 2025 **[BORDERLINE]**) for the downward direction: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Its example: a "build a Flappy Bird clone" task split in two, where "subagent 1 actually mistook your subtask and started building a background that looks like Super Mario Bros." Copying the original task into the subagent is not enough because earlier turns and tool calls change how the task should be read. — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- Cognition's 2026 follow-up lists what went wrong when a manager Devin delegates to child Devins: managers are "overly prescriptive", which backfires when the manager lacks deep codebase context; agents assume shared state with children that does not exist; and children do not report back by default, which took dedicated work to fix. It names the open problems as communication problems: how a child surfaces a discovery that should change siblings' work, and how to transfer context without overloading the receiver. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- LangChain docs name a specific loss at the return hop: "A common failure mode is that the sub-agent performs tool calls or reasoning but doesn't include results in its final message"; the fix is to "remind it that the supervisor only sees the final output." — [LangChain docs, Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)
- Copilot CLI's production analysis found that delegated subagents hit failure-prone paths the main agent would not: stale file paths, moved files, incorrect relative paths and workspace mismatches, plus repeated or overlapping searches between main agent and subagent. — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)

**Depth limits in shipping products (read 2026-11-23)**

- Claude Code: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation. At the depth limit, Claude Code withholds the `Agent` tool from every subagent except a fork, so a subagent at the limit does its delegated work itself and returns one summary." The limit is set with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` ("Set `1` to turn nesting off."). To stop one subagent from spawning, "omit `Agent` from its `tools` list or add it to `disallowedTools`." — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Claude Code agent teams: "No nested teams: teammates cannot spawn their own teammates. Only the lead can manage the team." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Cursor (forum reply dated Aug 10, 2026, from a responder speaking for "our team"; no staff badge visible): "supported depth is main → L1 → L2", "An L2 subagent can't spawn further", and "Cloud Agents today effectively support one level from the main agent". Flat dispatch is called "still the most reliable pattern"; a middle orchestrator works only "if its prompt explicitly requires Task launches", because "What can feel flaky is an L1 orchestrator hesitating to delegate." — [Cursor forum, Official nesting depth for subagents](https://forum.cursor.com/t/official-nesting-depth-for-subagents-how-deep-is-reliable-in-current-cursor/167883)
- VS Code (page dated 11/18/2026): nested subagents are controlled by `chat.subagents.allowInvocationsFromSubagents`; "Local disables this by default", and when enabled it allows nesting "up to a maximum depth of five". Local subagent invocations are stateless: "follow-up work requires a new invocation with the relevant context." — [VS Code docs, Subagents](https://code.visualstudio.com/docs/copilot/agents/subagents)
- Google ADK: "Task mode agents must be leaf agents and cannot have subagents." — [ADK, Collaborative workflows](https://adk.dev/workflows/collaboration/)
- Devin: the manager pattern described is one manager level with child Devins, coordinated through an internal MCP; the post does not discuss deeper nesting. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Evidence that recursion can work at scale: in Cursor's planner/worker/judge system, planners "can spawn sub-planners for specific areas, making planning itself parallel and recursive" (recursion depth not stated). Note that only planning recursed; workers were leaves. The same post reports that an added integrator role "created more bottlenecks than it solved" and was removed, and that "Many of our improvements came from removing complexity rather than adding it." — [Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)

**Documented mitigations**

- Files instead of messages, references instead of content: "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator", "Rather than requiring subagents to communicate everything through the lead agent". — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Condensed returns: a subagent "might explore extensively, using tens of thousands of tokens or more," but "returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)"; agents should "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load data just in time. (Sep 29, 2025) — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- File-based communication between planner, generator and evaluator, and a "sprint contract" defining what "done" means before work starts; context resets need "a structured handoff artifact carrying state and next steps". — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Pass-through of results without paraphrase (`forward_message`) and keeping routing chatter out of the sub-agent's context. — [LangChain, Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)
- Decompose by context, not by role: "an agent handling a feature should also handle its tests", and "Work should only be split when context can be truly isolated." Good boundaries: independent research paths, components with clean interfaces, black-box verification. Poor boundaries: sequential phases of the same work, tightly coupled components, work requiring shared state. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Fork the full context instead of summarising it when the receiver must not miss anything: Cognition's "80/20" choice for the smart-friend pattern is to share a fork of the primary's full context, because sharing a subset leads to uninformed answers. Claude Code's fork subagent similarly "inherits the parent conversation instead of starting fresh". — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working); [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Orientation artifacts for agents that start cold: READMEs and progress files, because each agent starts with no context. — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- Persist shared state externally "rather than relying only on in-memory context"; "Validate agent output before you pass it to the next agent. Low-confidence, malformed, or off-topic responses can cascade through a pipeline." — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Adjacent academic results (snippet only, not read): an EffGen paper reportedly measured communication overhead at nesting depths 1-5 as under 0.3% of end-to-end latency (latency, not fidelity) — [arXiv 2602.00887](https://arxiv.org/pdf/2602.00887); a decision-theoretic paper models intermediate stages that only relay evidence as adding no information for the final decision — [arXiv 2603.26993](https://arxiv.org/html/2603.26993v1).

### Inferences
- Depth compounds the per-hop losses that are documented for a single hop: each level paraphrases the brief on the way down and the result on the way up. With centralized error amplification of 4.4x for one orchestrator layer (Kim et al.), there is no evidence that a second or third orchestrating layer keeps it that low; vendor defaults of 1-3 layers are consistent with that caution.
- The one documented case of successful recursion (Cursor's sub-planners) recursed over planning only, on a shared artifact (the codebase and task list), with leaf workers that write. That suggests depth is tolerable when intermediate nodes own a planning scope and communicate through durable artifacts, and risky when intermediate nodes are pure relays.
- A middle layer earns its place only if it holds context the parent should not hold (for example one repository's conventions and state). A middle layer that just forwards a brief and a summary adds two paraphrasing hops and no information.
- For a pipeline that spans stages, the artifact of each stage (refined requirement, spec, plan) is the natural handoff object: later levels should be given the file path, not a parent-written digest of it.
- Technical latency of nesting appears negligible; the cost of depth is fidelity and tokens, not message transport.

### Gaps
- No empirical study measuring coding-task success or information fidelity versus nesting depth (2, 3, 4+ levels) was found; a targeted search returned only theory, product documentation and commentary. This is the largest evidence gap for the stated use case.
- Claude Code's nesting history is disputed in third-party posts (reports of a depth cap of five in a mid-2026 release, a temporary ban, then a default of three); only the current official documentation (default three layers, configurable) was verified, not the changelog.
- OpenAI Codex's depth setting could not be confirmed: the current subagents page does not mention a depth key (it mentions `agents.max_threads` only as a legacy alias). Earlier Codex documentation is recalled as having an `agents.max_depth` setting, but this was not verified.
- GitHub Copilot CLI's nesting behaviour is not stated in the docs pages read; a community learning page says subagents do not spawn subagents by default, and the nesting switch it names is the VS Code setting.

## 3. What do the main vendors and frameworks recommend?

### Takeaway
The vendors have converged more than their 2025 positions suggested: one agent by default; extra agents for isolated read-heavy work, independent verification, and genuinely parallel work; a single writer per piece of state; summaries and artifacts flowing back to one coordinator. They differ mainly on how much nesting to allow and on whether children may talk to the user.

### Cited Findings

**Anthropic**

- "we recommend finding the simplest solution possible, and only increasing complexity when needed"; "Agentic systems often trade latency and cost for better task performance". Three principles: "Maintain simplicity in your agent's design", "Prioritize transparency by explicitly showing the agent's planning steps", and carefully craft the agent-computer interface. (Dec 19, 2024 **[OLD]**) — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Multi-agent fits breadth-first, parallelizable, high-value work; poor fits are "domains that require all agents to share the same context" or with "many dependencies between agents", and "most coding tasks involve fewer truly parallelizable tasks than research". (Jun 13, 2025 **[BORDERLINE]**) — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Three situations where multiple agents consistently win: context protection, parallelization ("The primary benefit of parallelization is thoroughness, not speed."), and specialization; "Outside these situations, the coordination costs typically exceed the benefits." Teams built elaborate multi-agent systems only to find "improved prompting on a single agent achieved equivalent results." (Jan 23, 2026) — [Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Choice of long-horizon technique: "Compaction maintains conversational flow for tasks requiring extensive back-and-forth;" "Note-taking excels for iterative development with clear milestones;" "Multi-agent architectures handle complex research and analysis where parallel exploration pays dividends." (Sep 29, 2025) — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "every component in a harness encodes an assumption about what the model can't do on its own", so components should be re-tested as models improve; with Opus 4.5/4.6 the sprint decomposition and context resets were dropped, the planner stayed (without it "the generator under-scoped"), and the evaluator became conditional. (Mar 24, 2026) — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Claude Code subagents: use the main conversation when "The task needs frequent back-and-forth or iterative refinement", when "Multiple phases share significant context, such as planning, implementation, and testing", for quick targeted changes, or when latency matters; use subagents when "The task produces verbose output you don't need in your main context", when you want to enforce tool restrictions, or when "The work is self-contained and can return a summary". — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Claude Code agent teams (experimental): best for research and review, new modules where teammates own separate pieces, debugging with competing hypotheses, and cross-layer work; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)

**Cognition**

- 2025 position: the simplest way to follow the context principles "is to just use a single-threaded linear agent"; "in 2025, running multiple agents in collaboration only results in fragile systems." It noted that Claude Code's subagent "never does work in parallel with the subtask agent" and "is usually only tasked with answering a question, not writing any code." (Jun 12, 2025 **[BORDERLINE]**) — [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- 2026 revision: the earlier observations still hold for parallel-writer swarms; what works is where "multiple agents contribute intelligence to a task while writes stay single-threaded." Most real-world multi-agent setups are read-only subagents that "mostly resemble tool calls rather than true multi-agent collaboration". (Apr 22, 2026) — [Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)

**OpenAI**

- Codex: "Current Codex releases enable subagent workflows by default." "As a starting point, use parallel agents for read-heavy tasks such as exploration, tests, triage, and summarization." "Be more careful with parallel write-heavy workflows". "Return summaries from subagents instead of raw intermediate output." Built-in roles: `default`, `worker` ("execution-focused agent for implementation and fixes"), `explorer` ("read-heavy codebase exploration agent"). "Subagents inherit the parent turn's current sandbox and approval settings". — [Codex docs, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Agents SDK: use agents-as-tools when "a specialist should help with a bounded subtask but should not take over the user-facing conversation"; use handoffs when the specialist should "own the remainder of the current turn". Tactics: "Invest in good prompts.", "Have specialized agents that excel in one task, rather than having a general purpose agent.", "Invest in evals". — [OpenAI Agents SDK, Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)

**Google**

- ADK collaborative workflows: "a coordinator agent handles delegation of tasks to one or more subagents"; sub-agent modes are chat, task and single-turn; "Each task or single-turn mode agent operates in its own isolated session branch"; parallel agents "cannot see what its peer agents are doing." — [ADK, Collaborative workflows](https://adk.dev/workflows/collaboration/)

**LangChain / LangGraph**

- "not every complex task requires this approach"; "a single agent with the right (sometimes dynamic) tools and prompt can often achieve similar results." "At the center of multi-agent design is context engineering—deciding what information each agent sees." — [LangChain docs, Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- Supervisor is the most generic architecture because it makes the fewest assumptions about sub-agents, but a naive implementation underperforms; "We always recommend starting from your goals (definitions of success) and constraints when picking a design pattern." (Jun 2025 **[BORDERLINE]**) — [LangChain, Benchmarking multi-agent architectures](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)

**Microsoft**

- "Use the lowest level of complexity that reliably meets your requirements." "If a single agent can reliably solve your scenario, consider adopting that approach. Decision-making and flow-control overhead often exceed the benefits of breaking the task into multiple agents." Listed antipatterns include "Adding agents that don't provide meaningful specialization", "Overlooking latency impacts of multiple-hop communication", and "Sharing mutable state between concurrent agents". Patterns may be combined per stage: "Don't try to make one workflow fit into a single pattern when different stages of your workload have different characteristics". — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

**GitHub Copilot**

- Copilot CLI ships seven built-in agents the main agent can delegate to (explore, task, general-purpose, code-review, research, rubber-duck, security-review); "A subagent is an agent doing delegated work in a separate context window"; "Independent tasks can also run in parallel." Repository instructions "are not included for a custom subagent by default." — [GitHub Docs, About custom agents (Copilot CLI)](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents)
- `/fleet`: the main agent "analyzes the prompt and determines whether it can be divided into smaller subtasks", assigns them to subagents, runs independent ones in parallel, then reviews and combines results. "If your request is inherently sequential, using `/fleet` may not provide any benefit." Planning first is recommended: "planning before delegation can clarify the goal, divide it into manageable subtasks, and reveal dependencies." — [GitHub Docs, Delegating and parallelizing work with agents](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/delegating-and-parallelizing-work-with-agents)
- Copilot CLI's own delegation policy after the June 2026 change: "Copilot CLI should handle focused work directly: find a file, read it, make a targeted change, and verify it." Delegation is for work needing independent context, broad exploration, or parallel execution; "Subagents should be treated as a parallelism tool, not a pause button." (rolled out in CLI 1.0.42+) — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- VS Code: "Delegate work with a clear scope and a result the main agent can use." "For a quick lookup or a small edit, a direct request is usually enough." "Separate contexts don't guarantee separate files." — [VS Code docs, Subagents](https://code.visualstudio.com/docs/copilot/agents/subagents)

### Inferences
- The Cognition/Anthropic disagreement of mid-2025 has largely closed: both now endorse read-only helpers, clean-context reviewers and a single-writer rule, and both report manager/child delegation as workable but communication-limited.
- Every vendor frames the planner stage as worth keeping even with strong models (Anthropic's planner, Copilot's `/plan` before `/fleet`, Cursor's planners, Magentic-One's ledger), while decomposition scaffolding around the implementer is being removed as models improve. That favours spending hierarchy on planning and verification, not on splitting implementation finely.

### Gaps
- A2A (Google's agent-to-agent protocol) was not researched in this session; no claim about it is made here.
- Microsoft Agent Framework's own orchestration and human-in-the-loop pages were not read; only the Azure Architecture Center guidance and the 2024 Magentic-One article were.
- The GitHub Copilot coding agent (cloud) and its custom-agent behaviour were not examined separately from Copilot CLI and VS Code.
- LangGraph's dedicated "hierarchical teams" tutorial was not re-read; the current LangChain multi-agent page does not discuss nested supervisors.

## 4. What failure taxonomies exist, and which failure modes matter most for a coordinator that plans and delegates coding work?

### Takeaway
MAST (UC Berkeley, NeurIPS 2025) is the standard taxonomy: 14 failure modes in three categories over 1,600+ annotated traces from seven frameworks, with system-design issues the largest share (about 44%), inter-agent misalignment about 32% and verification about 24%. For a planning-and-delegating coordinator the most relevant modes are disobeying the task specification, step repetition, not knowing when to stop, failing to ask for clarification, reasoning-action mismatch, and missing or wrong verification.

### Cited Findings

- MAST defines 14 failure modes in 3 categories, built from 1,642 annotated traces across 7 frameworks (MetaGPT, ChatDev, HyperAgent, AppWorld, AG2/MathChat, Magentic-One, OpenManus); human inter-annotator agreement was kappa = 0.88, and an LLM annotator reached kappa = 0.77 against experts. First posted Mar 2025 **[OLD for v1]**; v3 and the NeurIPS 2025 version expanded the dataset from about 150-200 traces to 1,600+. — [Cemri et al., Why Do Multi-Agent LLM Systems Fail? (v3)](https://arxiv.org/html/2503.13657v3)
- Per-mode prevalence in v3. System design: FM-1.1 disobey task specification 11.8%, FM-1.2 disobey role specification 1.5%, FM-1.3 step repetition 15.7%, FM-1.4 loss of conversation history 2.8%, FM-1.5 unaware of termination conditions 12.4%. Inter-agent misalignment: FM-2.1 conversation reset 2.2%, FM-2.2 fail to ask for clarification 6.8%, FM-2.3 task derailment 7.4%, FM-2.4 information withholding 0.85%, FM-2.5 ignored other agent's input 1.9%, FM-2.6 reasoning-action mismatch 13.2%. Task verification: FM-3.1 premature termination 6.2%, FM-3.2 no or incomplete verification 8.2%, FM-3.3 incorrect verification 9.1%. Category totals are sums of these (about 44.2% / 32.3% / 23.5%); the same three values appear in the paper's figure text. — [Cemri et al. (v3)](https://arxiv.org/html/2503.13657v3)
- MAST's conclusion: "MAS failure is not merely a function of challenges in the underlying model"; the authors conjecture that "improvements in the base model capabilities will be insufficient to address the full MAST". Interventions on ChatDev: improved role specification / final-say workflow gave +9.4% task success and adding a high-level task-objective verification step gave +15.6%, yet completion rates stayed low. — [Cemri et al. (v3)](https://arxiv.org/html/2503.13657v3)
- Error amplification as a quantitative failure measure: errors propagate unchecked among independent agents (17.2x) and a central orchestrator acts as a validation bottleneck (4.4x). — [Kim et al.](https://arxiv.org/html/2512.08296v2)
- Coordination failures observed in coding swarms (Cursor): with locks, "Agents would hold locks for too long, or forget to release them entirely" and "Twenty agents would slow down to the effective throughput of two or three"; "With no hierarchy, agents became risk-averse", making small safe changes and avoiding hard tasks; too little structure makes agents "conflict, duplicate work, and drift", too much "creates fragility". — [Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)
- Parallel-writer collision (Anthropic C compiler): "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes." — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- Self-evaluation bias: "agents reliably skew positive when grading their own work." — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Verifier failure, the "early victory" problem: the main failure mode of verification subagents is "marking outputs as passing without thorough testing"; mitigations are concrete criteria, comprehensive checks, negative tests and an explicit instruction to run the complete test suite. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Wrong-target failure: "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- Delegation-specific failures in a production coding CLI: over-delegation of simple work ("Work that should have taken one step now takes three."), overuse of exploration subagents when the handoff already had enough context, duplicated searches, and the main agent waiting on subagents sequentially instead of working in parallel. — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- Manager-specific failures (Devin): over-prescriptive managers, assumed shared state, children that do not report back. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Team-coordination failures documented for Claude Code agent teams: "teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; the lead may start implementing instead of waiting, or decide "the team is finished before all tasks are actually complete"; "Teammates may stop after encountering errors instead of recovering." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Stateful error compounding: "Agents are stateful and errors compound", addressed by building "systems that can resume from where the agent was when the errors occurred." — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Mapping MAST to a plan-and-delegate coordinator: FM-1.1 (child drifts from the brief), FM-1.3 (re-doing work the parent or a sibling already did; the Copilot "repeated searches" finding is the production form), FM-1.5 and FM-3.1 (stopping early or never), FM-2.2 (child guesses instead of asking, which is structurally encouraged when children cannot reach the human), FM-2.6 (child reports something other than what it did), and FM-3.2/3.3 (parent accepts an unverified "done"). FM-1.4 and FM-2.1 are less relevant when each child has its own persistent session.
- Verification failures (about a quarter of MAST failures) and the documented positive bias of self-grading make an independent check of each child's claim the highest-leverage structural addition; the largest single MAST intervention gain (+15.6%) came from adding exactly such a step.
- A tree deepens two MAST modes mechanically: every extra level is another place for FM-2.2 (a question that is not passed up) and FM-2.4 (a finding that is not passed up).

### Gaps
- MAST's dataset is dominated by 2023-2024 era frameworks and models; no later re-annotation on 2026 coding agents (Claude Code, Codex, Devin, Copilot CLI) was found.
- Only the first 100,000 characters of the MAST v3 page were read; per-framework failure rates (e.g. ChatDev correctness) are in figures not captured here.
- No taxonomy specific to nested (depth > 1) delegation was found.

## 5. When should work be delegated to a child versus kept in the parent? Read-heavy vs write-heavy, parallel vs sequential, how many children

### Takeaway
Delegate when the work is self-contained, produces more context than the parent needs, or can truly run in parallel; keep it in the parent when it is small, iterative, or shares context with adjacent phases. Read-heavy work parallelizes safely; write-heavy work should have one writer per file set (or per isolated worktree). Practical fan-out is 3-5 concurrent children, with reported degradation beyond about 3-4 agents under a fixed budget.

### Cited Findings

**Keep in parent / do it directly**

- Use the main conversation when "The task needs frequent back-and-forth or iterative refinement", when "Multiple phases share significant context, such as planning, implementation, and testing", for "a quick, targeted change", or when latency matters, since a non-fork subagent "starts fresh and may need time to gather context". — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- "Copilot CLI should handle focused work directly: find a file, read it, make a targeted change, and verify it." Start with the narrowest effective path, escalate when complexity justifies it, and step back down once the task is focused again. — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- Coordination pays less the better a single agent already does: returns diminish or turn negative above a single-agent baseline of about 45%, and sequential planning tasks lost 39-70% under every multi-agent architecture. — [Kim et al.](https://arxiv.org/html/2512.08296v2)

**Delegate**

- Use subagents when "The task produces verbose output you don't need in your main context", "You want to enforce specific tool restrictions or permissions", or "The work is self-contained and can return a summary". — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Context isolation pays off when a subtask generates "high context volume (more than 1000 tokens)" most of which is irrelevant to the main task; in the example given, the main agent receives "the 50-100 tokens it actually needs" instead of 2000+ tokens of history. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns to your main conversation" (running tests, fetching documentation, processing logs). — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- Subagents beat in-context skills on long tasks "when skills have clear input-output contracts and instructions that encode the needed procedural knowledge", at the cost of extra coordination tokens (abstract only, Sep 7, 2026). — [Piriyakulkij et al., Subagents vs Agent Skills](https://arxiv.org/abs/2609.09233)

**Read-heavy vs write-heavy**

- "use parallel agents for read-heavy tasks such as exploration, tests, triage, and summarization" and "Be more careful with parallel write-heavy workflows", because agents editing code at once can create conflicts. — [Codex docs, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Writes stay single-threaded; extra agents contribute intelligence (search, review, advice), not parallel actions. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." For newcomers: "start with tasks that have clear boundaries and don't require writing code: reviewing a PR, researching a library, or investigating a bug." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- "Separate contexts don't guarantee separate files." Conversations sharing a folder or worktree can affect the same code. — [VS Code docs, Subagents](https://code.visualstudio.com/docs/copilot/agents/subagents)
- Parallel writing can work when the work is partitioned by an oracle or by files: the C-compiler agents collided on one bug until GCC was used as a known-good oracle to split the kernel build into independently fixable files. — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

**Parallel vs sequential**

- "Delegate independent work in parallel only when the tasks don't depend on each other's results." — [VS Code docs, Subagents](https://code.visualstudio.com/docs/copilot/agents/subagents)
- "If your request is inherently sequential, using `/fleet` may not provide any benefit." — [GitHub Docs, Delegating and parallelizing work with agents](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/delegating-and-parallelizing-work-with-agents)
- While a subagent runs, the main agent should keep working on independent tasks rather than waiting ("a parallelism tool, not a pause button"). — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- Synchronous waiting is a known bottleneck: "Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding." — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Parallel tool calling "cut research time by up to 90% for complex queries", but the January 2026 guidance warns the main benefit of parallel agents is thoroughness and that total execution time is often longer. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)

**How many children**

- Effort scaling rules embedded in the lead's prompt: "Simple fact-finding requires just 1 agent with 3-10 tool calls", "direct comparisons might need 2-4 subagents with 10-15 calls each", "complex research might use more than 10 subagents". — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- "Start with 3-5 teammates for most workflows." "If you have 15 independent tasks, 3 teammates is a good starting point." "Three focused teammates often outperform five scattered ones." "Having 5-6 tasks per teammate keeps everyone productive". Task sizing: too small and "coordination overhead exceeds the benefit"; too large and "teammates work too long without check-ins, increasing risk of wasted effort"; right-sized tasks are "self-contained units that produce a clear deliverable, such as a function, a test file, or a review". — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Per-agent reasoning capacity becomes "prohibitively thin" beyond about 3-4 agents under fixed budgets; turns grow with exponent 1.724 in agent count. — [Kim et al.](https://arxiv.org/html/2512.08296v2)
- "Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own while it runs." — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
- A workable decision rule that is consistent with all sources: delegate if (a) the work can be specified without the parent's conversation, (b) its intermediate output is large relative to what the parent needs back, and (c) it either can run alongside other work or needs a clean context (review). Otherwise do it in place.
- Pipeline stages that the vendors say share context (planning, implementation, testing of one change) are the wrong place to cut. A cut between "understand this repository" (read-heavy, returns a summary) and "decide the cross-cutting design" (parent) is a right place; so is a cut between "implement" and "independently verify".
- Implementation fan-out is safest when each writing child owns a disjoint file set or its own worktree and a verifiable definition of done; where two children would touch the same files, sequence them.
- Fan-out of 3-5 per parent and a small depth implies a hard ceiling on total concurrent agents in a tree; with super-linear turn growth the budget is better spent on fewer, better-briefed children.

### Gaps
- No source gives a measured optimum number of concurrent children for coding work; the 3-5 guidance is vendor heuristics and the 3-4 figure comes from non-coding benchmarks at a fixed token budget.
- No quantitative comparison of worktree-isolated parallel writers versus sequential writers was found.

## 6. What should a delegation brief contain, and what should a child return?

### Takeaway
A brief must stand alone, because a child sees nothing else: objective, what is already known, scope and ownership boundaries, tools/sources, and the exact shape of the result expected. A return should be a short distilled summary (the cited range is about 1,000-2,000 tokens) with pointers to artifacts on disk, and the child must be told that only its final message is seen.

### Cited Findings

**Brief contents**

- "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." The post also embeds effort-scaling rules in the lead's prompt so that it sizes delegation correctly. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Copilot CLI's revised handoff rule: handoffs should state what the user asked, what is already known, what the subagent owns, and what result the main agent needs back. — [GitHub Blog, selective delegation](https://github.blog/ai-and-ml/github-copilot/how-we-made-github-copilot-cli-more-selective-about-delegation/)
- Why the brief must be self-contained: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there." — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Example of a good spawn prompt naming the target path, focus areas, relevant architecture fact and the expected output: "Review the authentication module at src/auth/ for security vulnerabilities. Focus on token handling, session management, and input validation. The app uses JWT tokens stored in httpOnly cookies. Report any issues with severity ratings." Teammates "don't inherit the lead's conversation history"; and "everything in the spawn prompt adds to their context from the start", so prompts should stay focused. — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams); [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- Do not over-specify the "how": managers that are "overly prescriptive" backfire when the manager lacks deep codebase context. For questions to a stronger model, broad questions ("what should I do?") worked better than narrow ones. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Input options: "Passing only the task description (`query`) keeps the subagent isolated", while passing the parent's history "seeds the subagent with prior work, which helps when it needs to continue something the parent already started." — [LangChain docs, Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)
- Decide per hop whether the next agent needs "the full, raw context gathered so far", "a compacted version, such as a summary of prior agent outputs", or only "a new instruction set"; prefer the last when it suffices. — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Agree the definition of done up front: a "sprint contract" between generator and evaluator defined what "done" meant before each sprint, with hard thresholds ("If any one fell below it, the sprint failed."). — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Project-level instructions may not reach the child automatically: in Copilot CLI repository instructions "are not included for a custom subagent by default." — [GitHub Docs, About custom agents (Copilot CLI)](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents)

**What the child returns**

- A "condensed, distilled summary of its work (often 1,000-2,000 tokens)" after using "tens of thousands of tokens or more". — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Return summaries from subagents instead of raw intermediate output." — [Codex docs, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Artifacts by reference: subagents "store their work in external systems, then pass lightweight references back to the coordinator." — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Two ways to control the return: "Prompt the sub-agent: Specify exactly what should be returned." and "Format in code: Adjust or enrich the response before returning it." Because the "supervisor only sees the final output", tell the child so. — [LangChain docs, Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)
- Structured outputs make results checkable: generate "well formed data that you can inspect with your code." — [OpenAI Agents SDK, Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)
- Parent-side filtering of what comes back: Devin uses its fuller knowledge of user instructions and prior decisions to filter the bugs the reviewer returns, which prevents looping, disobeying the user and out-of-scope work. — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- Surfacing problems is part of the return: "Surface errors instead of hiding them, so downstream agents and orchestrator logic can respond appropriately." — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Continuing instead of re-briefing: in Claude Code "Resumed subagents retain their full conversation history, including all previous tool calls, results, and reasoning", whereas each new invocation "creates a new instance". VS Code local subagents are stateless per invocation. — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents); [VS Code docs, Subagents](https://code.visualstudio.com/docs/copilot/agents/subagents)
- Machine-readable output discipline for agents that read results: minimal console output and errors tagged for grep were used so that agents were not flooded. — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

### Inferences
- A consolidated brief template supported by the sources: (1) the goal and why it matters to the larger task; (2) what is already known or decided, with file paths to the governing artifacts (spec, plan) rather than a paraphrase; (3) what this child owns and must not touch; (4) constraints and conventions it cannot discover cheaply; (5) the definition of done and how it will be verified; (6) the return format and length, and the instruction that only the final message is seen; (7) what to do when blocked or when an assumption fails (return a structured "needs input" rather than guess).
- A consolidated return template: outcome (done / partial / blocked), what changed (paths, branch or commit references), evidence (commands run and their results, not assertions), deviations from the brief and decisions made, open questions, and anything the parent or siblings should know. Keeping it to roughly one or two thousand tokens with references keeps the parent's context small; the evidence section is what lets the parent check the claim without re-reading the child's transcript.
- In a three-level tree the middle node should pass the grandchild's artifact references upward unchanged and add only its own synthesis, mirroring LangChain's `forward_message` result that removing a paraphrase hop materially improved accuracy.
- Where the platform allows resuming a child with its history, follow-up work is cheaper and higher-fidelity as a continuation than as a fresh brief.

### Gaps
- No published experiment isolates the effect of brief quality or return format on coding-task success; the guidance is engineering practice plus one benchmark on supervisor relay.
- The 1,000-2,000 token return size is a description of practice, not a tested optimum.

## 7. How do role separation and model tiering work in practice?

### Takeaway
Two tiering directions are documented: a strong orchestrator with cheaper workers (the classic form, with measured wins in research and long-running builds) and a cheap executor that consults a strong advisor (measured: +2.7 points on SWE-bench Multilingual with 11.9% lower cost). The best-supported role separation is an independent reviewer with clean context, which works because it is not anchored on the implementer's reasoning; the main risks are a weak model not knowing when to escalate and a reviewer that passes work too easily.

### Cited Findings

**Strong orchestrator, cheaper workers**

- Opus 4 lead with Sonnet 4 subagents outperformed single-agent Opus 4 by 90.2% on an internal research eval. (Jun 2025 **[BORDERLINE]**) — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- "Assign each agent a model that matches the complexity of its task. Not every agent requires the most capable model. Agents that perform classification, extraction, or formatting can often use smaller, less expensive models without a reduction in overall quality." — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Claude Code: "Use Sonnet for teammates. It balances capability and cost for coordination tasks."; "For simple subagent tasks, specify `model: haiku` in your subagent configuration." Model and effort can be set per subagent definition or per invocation; precedence is the per-invocation `model` parameter, then the definition's `model`, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the parent's model ("or the spawning subagent's model for a nested subagent"). — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs); [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Role-specific model choice at scale: Cursor found one model "much better at extended autonomous work" and a better planner than a coding-specialised sibling, another that "tends to stop earlier and take shortcuts when convenient", and now uses the model best suited to each role. (Jan 2026; the specific models named are already superseded.) — [Cursor, Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)
- Cost structure of a planner/generator/evaluator run: planning and QA are cheap relative to building ($0.46 planner and about $10.39 total QA versus about $113.85 building in a $124.70 run). — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**Cheap executor, strong advisor (inverted tiering)**

- Anthropic's advisor strategy (Apr 9, 2026): "pair Opus as an advisor with Sonnet or Haiku as an executor"; "This inverts a common sub-agent pattern"; "a smaller, more cost-effective model drives and escalates without decomposition, a worker pool, or orchestration logic." Sonnet with an Opus advisor scored 2.7 percentage points higher on SWE-bench Multilingual than Sonnet alone while cost per agentic task fell 11.9%. Haiku with an Opus advisor scored 41.2% on BrowseComp versus 19.7% solo. Advisor output is typically 400-700 text tokens. — [Claude blog, The advisor strategy](https://claude.com/blog/the-advisor-strategy)
- Cognition's "smart friend" experience: the pattern failed with a sub-frontier primary model, which "was not good enough at being the primary model for this setup to really work", because a weaker model struggles to know when it is at its limits and what to ask. Mitigations: always make at least one call to the strong model, train or tune for calibration, or add domain rules (e.g. always escalate merge conflicts). "smart-friend works today when both models are strong." Cross-vendor pairings worked as "a capability router rather than a difficulty escalator". — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)

**Independent reviewer**

- Devin Review, a separate agent with no shared context, catches "an average of 2 bugs per PR", about 58% of them severe (logic errors, missing edge cases, security vulnerabilities). The reviewer works best sharing no context with the coder: it sees only the diff, must reason backward from the implementation, can question choices the coder accepted, and is free of the coder's long, rotted context. "clean context leads to a notable improvement in capabilities when using a generator-verifier loop." — [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)
- "agents reliably skew positive when grading their own work", and "tuning a standalone evaluator to be skeptical turns out to be far more tractable" than making a generator self-critical. But: "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." — [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- "Verification subagents succeed because they sidestep the telephone game problem"; they remain useful "when using less capable orchestrators, when verification requires specialized tools," or to enforce checkpoints, while stronger models can increasingly evaluate subagent work directly. Their main failure is passing work without thorough testing. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Anchoring is the stated reason for independent parallel investigators: "Sequential investigation suffers from anchoring: once one theory is explored, subsequent investigation is biased toward it." Splitting review into distinct lenses (security, performance, test coverage) is recommended because "A single reviewer tends to gravitate toward one type of issue at a time." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Maker-checker loops need "clear acceptance criteria for the checker agent", "an iteration cap to prevent infinite refinement loops", and a fallback such as "escalation to a human reviewer". — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Enforcing a read-only reviewer by tool restriction: omit the spawn tool (and edit tools) from the reviewer's tool list. — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Specialization can beat generality in delegation benchmarks: sub-agent specialization was the best practical variant in MS-Eval (abstract only). — [Ding et al., MS-Eval](https://arxiv.org/abs/2610.22869)

### Inferences
- The reviewer should receive the artifact (diff, spec) and the acceptance criteria, not the implementer's narrative; giving it the implementer's reasoning recreates the anchoring that the clean context is meant to remove. Conversely, the party that decides which review findings to act on should be the one holding the fuller context (the parent), as in Devin's filtering step.
- Spend the expensive model where errors are costly to recover from and tokens are few: planning, cross-cutting design decisions and review. The cost breakdown from Anthropic's harness (planner under 1% of spend, QA about 8%) shows this is affordable.
- A cheap implementer is safe only with a strong verification step or an escalation path; the Cognition evidence says self-initiated escalation by a weak model is unreliable, so escalation should be rule-based or mandatory at defined points.
- Review rounds need an iteration cap and a human fallback; otherwise generator-verifier loops run long (Cognition notes loops can take several cycles; Anthropic's ran 5-15 iterations and up to four hours in frontend experiments).

### Gaps
- No controlled study compares "strong orchestrator + cheap workers" with "cheap executor + strong advisor" on the same coding benchmark.
- The Devin Review figures are vendor-reported and have no stated false-positive rate.
- Model-specific findings (which model plans best, which stops early) date quickly; the Cursor observations concern models from late 2025.

## 8. How should human-in-the-loop approval gates be placed in a hierarchy? Who may ask the human, and how do questions bubble up from a grandchild?

### Takeaway
The documented consensus is that the human talks to the root (or sees every request labelled with its source), that tool-permission prompts bubble up automatically while clarifying questions generally do not, and that another agent's message never counts as human consent. Two mechanisms exist for a child's question: return a structured "needs input" result so the parent re-dispatches with the answer, or let the child interrupt in place; mandatory gates should sit at persisted checkpoints between stages and at risky tool calls rather than on every agent output.

### Cited Findings

**Who can reach the human**

- Claude Code removes `AskUserQuestion` from subagents' tools even when it is listed in the subagent's `tools` field; permission prompts are different: for foreground subagents "Permission prompts are passed through to you as they come up", and for background subagents "Claude Code surfaces the prompt in your main session and names the subagent that is asking." — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Agent teams: "Teammate permission prompts appear in the lead session, so approve them there yourself"; "Teammate permission requests bubble up to the lead, which can create friction. Pre-approve common operations in your permission settings before spawning teammates to reduce interruptions." The human can also message any teammate directly. — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Codex: "In interactive CLI sessions, approval requests can surface from inactive agent threads even while you are looking at the main thread." "The approval overlay shows the source thread label, and you can press `o` to open that thread before you approve, reject, or answer the request." "In non-interactive flows, or whenever a run can't surface a fresh approval, an action that needs new approval fails and Codex surfaces the error back to the parent workflow." Subagents inherit the parent turn's sandbox and approval settings. — [Codex docs, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Google ADK makes human access a property of the sub-agent's mode: chat mode "Full interaction", task mode "For clarification only", single-turn mode "Disallowed". — [ADK, Collaborative workflows](https://adk.dev/workflows/collaboration/)
- LangChain: subagents normally return to the main agent, but "you can use interrupts within a subagent to allow user interaction", which is "useful when a subagent needs clarification or approval before proceeding"; "The main agent remains the orchestrator, but the subagent can collect information from the user mid-task." Its pattern table rates Subagents lowest (one star) for direct user interaction. — [LangChain docs, Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents); [LangChain docs, Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- OpenAI Agents SDK: agents-as-tools is for a specialist that "should not take over the user-facing conversation"; a handoff is for when the specialist should own the rest of the turn. — [OpenAI Agents SDK, Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)

**Agent messages are not consent**

- "When one agent sends another a message over `SendMessage`, Claude Code tells the receiving agent the message came from another Claude session, not from you. A teammate can't approve a permission prompt or supply consent on your behalf, and a teammate that was denied an action can't relay it to another teammate to bypass the check." In auto mode the classifier "treats an approval claim relayed from another agent as untrusted input rather than confirmation from you." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)

**Where to put gates**

- "Identify which points require human input, decide if that input is optional or mandatory, and determine whether the human response is an approval that advances the workflow or feedback that loops back to the agent for refinement. Mandatory gates make the orchestration synchronous at that step, so persist state at these checkpoints to resume operation without a replay of prior agent work. You can also scope HITL gates to specific tool invocations rather than full agent outputs so that the orchestration can proceed autonomously for low-risk actions." — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- Magentic orchestration is suited to "A requirement for the AI system to generate a fully developed plan of approach that a human can review before or after implementation." — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- "Agents can then pause for human feedback at checkpoints or when encountering blockers." and "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." (Dec 2024 **[OLD]**) — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Plan-before-implement as a gate: "Use plan mode for complex tasks ... Claude explores the codebase and proposes an approach for your approval, preventing expensive re-work when the initial direction is wrong." — [Claude Code docs, Manage costs effectively](https://code.claude.com/docs/en/costs)
- A caution on delegated approval: in agent teams a teammate's plan approval request goes to the lead, and unless the teammate's permission mode was changed, "Claude Code approves the plan as soon as the request arrives, without the lead reviewing it"; "You aren't asked to approve it". — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Automated gates through hooks: `TaskCompleted` "runs when a task is being marked complete. Exit with code 2 to prevent completion and send feedback"; `TeammateIdle` and `TaskCreated` work the same way. — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Unattended running is discouraged: "Letting a team run unattended for too long increases the risk of wasted effort." — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)
- Design systems to "pause and seek human input before proceeding with such high-risk actions" (deleting files, sending email); in testing, agents tried to recruit outside human help on their own initiative. (Nov 2024 **[OLD]**) — [Microsoft Research, Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)
- Maker-checker fallback: when the iteration cap is reached, escalate to a human reviewer or return the best result with a quality warning. — [Microsoft Learn, AI agent orchestration patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)

**Bubbling a question up from a child (lower-confidence sources)**

- Snippet only (the page returned 404 when fetched): an architecture decision record in the Agora project argues for "request-stop-restart" — the sub-agent exits with a structured "needs input" result, the orchestrator routes the question to the right answerer (human, another agent, or data) and re-dispatches with the answer — over an in-flight ask, because the latter needs a bidirectional adapter and extra orchestrator state. — [Agora ADR-0008](https://quarrysystems.github.io/agora/explanation/decisions/0008-needs-input-request-stop-restart/)
- Snippet only: a pydantic-ai subagents package gives children an `ask_parent` tool; the task waits in a pending state while the parent answers, and questions per task are capped to prevent loops. — [subagents-pydantic-ai docs](https://vstorm-co.github.io/subagents-pydantic-ai/advanced/questions)
- Snippet only: the Scarab runtime routes escalations up the parent-child tree and "Only the root agent escalates to the human HITL gate". — [Scarab, Hierarchy and Escalations](https://scarab-project.github.io/scarab-runtime/operator-guide/hierarchy-escalations.html)
- Snippet only: a community-tracked Claude Code issue recommends having a subagent "return a structured result indicating that clarification is needed" because its question UI does not reach the user. — [claudeissues.com, issue 18721](https://claudeissues.com/issue/18721-docs-missing-warning-and-workflow-guidance-for-askuserquestion-limitation-in-sub)

### Inferences
- Two distinct channels should be designed separately. Permission/approval prompts for risky actions can go straight to the human from any depth provided they carry the asker's identity and position in the tree (the Claude Code and Codex model). Clarifying questions should climb one level at a time, because each ancestor may already hold the answer (the parent knows the spec, the root knows the user's intent); only the unanswered residue reaches the human.
- For clarifying questions from a grandchild, "return blocked with a structured question" (stop and re-dispatch, or resume the same child session with the answer) is the pattern with the least machinery and it fits platforms where a parent can continue a child with its history. It also turns MAST's "fail to ask for clarification" into an explicit, permitted outcome in the brief rather than something the child must improvise.
- Gate placement that follows from the sources: mandatory human approval at stage boundaries where an artifact is frozen (refined requirement, spec, plan) and before irreversible or outward-facing actions; no human gate on routine child completions, which should instead pass an automated check (tests, hooks) and an independent review. Persisting state at each gate makes waiting cheap.
- Approval must not be delegable down or sideways: a parent agent "approving" on the human's behalf is the failure the Claude Code docs explicitly guard against, and the auto-approved teammate plan shows how an apparent gate can be a no-op.
- Pre-approving common low-risk operations before fan-out reduces prompt fatigue, which otherwise scales with the number of concurrently running children.

### Gaps
- No vendor documents question routing through more than one intermediate level (grandchild -> child -> parent -> human); the multi-level pattern above is an inference from single-level mechanisms and three small open-source projects known only from search snippets.
- The fork section of the Claude Code subagents page and the Microsoft Agent Framework human-in-the-loop page were not read.
- No data was found on how often children's clarifying questions are answerable by an ancestor versus requiring the human, or on the cost of blocked children waiting for answers.
- How GitHub Copilot CLI surfaces a subagent's question or permission request to the user was not found in the pages read.
